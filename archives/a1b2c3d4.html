Kubernetes 命令参考手册

适用版本：Kubernetes v1.25+ | 工具：kubectl

概览：从组件关系到命令操作

在深入命令之前，先理解 Kubernetes 的核心组件关系和资源层次，这是高效使用 kubectl 的基础。

核心架构关系

Kubernetes 集群由控制平面和工作节点组成，各组件协同工作完成资源管理：

资源层次关系

Kubernetes 的资源存在明确的层次和依赖关系，理解这些关系有助于正确选择命令：

层次 资源类型 说明 典型操作
集群层 Node, Namespace, ResourceQuota 集群基础设施 节点维护、资源配额管理
工作负载层 Deployment, StatefulSet, DaemonSet, Job 应用部署与管理 扩缩容、滚动更新、回滚
应用层 Pod, Container 实际运行的应用实例 日志查看、exec 调试
服务层 Service, Ingress, NetworkPolicy 网络访问控制 服务暴露、流量路由
配置层 ConfigMap, Secret 配置与敏感数据 配置管理、密钥管理
存储层 PV, PVC, StorageClass 持久化存储 存储卷申请与绑定

kubectl 工作流程

kubectl 通过 kubeconfig 文件中的凭证（证书、Token）与 kube-apiserver 通信，所有操作最终通过 API Server 执行，确保操作的安全性和一致性。

一、命令基础与帮助系统

1.1 kubectl 架构与核心能力

kubectl 是 Kubernetes 的命令行工具，通过 kubeconfig 文件中的凭证信息与集群的 kube-apiserver 通信，实现对集群资源的全生命周期管理。其核心能力包括：

  • 部署与管理：使用 YAML/JSON 清单定义并创建 Deployment、Service、Pod、ConfigMap 等资源对象，支持创建、更新、删除和状态监控
  • 集群运维：管理节点、命名空间、存储卷、服务账户等集群基础设施，执行扩缩容和滚动更新
  • 调试排错：查看 Pod 日志、进入容器执行命令、获取集群事件、端口转发等
  • 资源监控：查看节点和 Pod 的 CPU/内存使用情况，辅助容量规划

1.2 基本语法

kubectl 的命令格式遵循统一规范，掌握这个结构就能举一反三：

位置 说明 示例
command 操作类型（动词） get, create, apply, delete, describe
TYPE 资源类型（大小写不敏感，支持单复数） pods, deployments, services
NAME 资源名称（省略则操作同类型所有资源） my-pod, nginx-deploy
flags 可选参数，用于调整命令行为 -n, -o, -l, --field-selector

命令与资源的对应关系：

  • get → 查看资源状态（最常用的命令）
  • describe → 查看资源详细信息和事件（排错常用）
  • create / apply → 创建/更新资源（声明式管理）
  • delete → 删除资源
  • edit / patch → 修改资源配置

四、工作负载管理

工作负载资源（Workload Resources）是管理 Pod 副本的控制器。直接操作 Pod 容易导致状态丢失，而使用工作负载控制器可以确保 Pod 始终处于期望状态。

4.1 Deployment

Deployment 是最常用的工作负载控制器，用于管理无状态应用的部署和滚动更新。

4.2 StatefulSet

StatefulSet 用于管理有状态应用，如数据库集群。它保证 Pod 的有序性和唯一性，每个 Pod 有稳定的网络标识和持久存储。

4.3 DaemonSet

DaemonSet 确保每个（或部分）节点上运行一个 Pod 副本，适用于系统级守护进程，如日志收集、监控代理等。

4.4 Job 与 CronJob

Job 用于执行一次性任务，CronJob 用于执行定时任务。

4.5 滚动更新与回滚

滚动更新是 Kubernetes 的核心能力之一，允许在不中断服务的情况下更新应用。

五、服务与网络

服务（Service）是 Kubernetes 的核心概念之一，它为 Pod 提供稳定的网络访问入口。即使 Pod 因扩容、故障等原因发生变化，Service 的 IP 地址保持不变。

5.3 NetworkPolicy

NetworkPolicy 用于控制 Pod 之间的网络流量，实现网络隔离和安全策略。

六、配置与存储

配置和存储是应用运行的基础。ConfigMap 用于存储非敏感配置，Secret 用于存储敏感数据，PV/PVC 用于持久化存储。

6.1 ConfigMap

ConfigMap 用于存储配置文件、环境变量等非敏感信息。

6.2 Secret

Secret 用于存储密码、密钥、证书等敏感信息，数据会进行 Base64 编码。

6.3 PV 与 PVC

PersistentVolume（PV）是集群级别的存储资源，PersistentVolumeClaim（PVC）是用户对存储资源的申请。

6.4 StorageClass

StorageClass 用于动态创建 PV，用户无需手动创建存储资源。

十、常见错误与解决方案

10.1 ImagePullBackOff / ErrImagePull

原因：镜像名称错误、镜像不存在、仓库认证失败、网络问题。

10.2 CrashLoopBackOff

原因：容器启动后立即崩溃，反复重启。

10.3 Pod 处于 Pending 状态

原因：资源不足、PVC 未绑定、节点选择器不匹配、污点容忍缺失。

10.4 NodeNotReady

原因：kubelet 未运行、网络故障、资源耗尽。

10.5 Pod 被驱逐（Evicted）

原因：节点资源（磁盘、内存）不足，kubelet 驱逐低优先级 Pod。

十一、最佳实践与建议

11.1 命令规范

  • 优先使用声明式管理：kubectl apply -f <manifest> 优于 kubectl create 和 kubectl run，便于版本控制和审计
  • 为资源添加标签：所有资源至少添加 app、env、version 标签，方便过滤和管理
  • 使用命名空间隔离环境：不同环境（dev/staging/prod）使用不同命名空间
  • 避免直接创建 Pod：使用 Deployment、StatefulSet 等控制器管理 Pod，确保自愈能力

11.2 安全管理

  • 避免在 kubeconfig 中使用集群管理员权限：为不同角色创建独立的 ServiceAccount 和 RBAC 绑定
  • 定期轮换证书和 Token：kubeadm 部署的集群证书有效期默认为 1 年
  • 使用 Secret 而非 ConfigMap 存储敏感数据：ConfigMap 的数据以明文存储
  • 限制 kubectl 的访问范围：通过 --as 参数模拟特定用户操作

11.3 运维效率建议

  • 配置命令补全：节省大量输入时间
  • 使用别名简化操作：
  • 善用 --watch 实时跟踪：kubectl get pods -w 实时观察 Pod 状态变化
  • 使用 --sort-by 排序输出：更直观地查看资源使用情况
  • 善用 --dry-run 生成模板：避免从头编写 YAML 文件
  • 保存常用命令为脚本：将复杂的排错命令保存为 shell 脚本，团队共享
