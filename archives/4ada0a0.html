Redis集群与高可用

本文基于我自己写的 redis-manage.sh 脚本中集群相关模块整理。日常运维中手动敲命令配置主从、哨兵和Cluster太繁琐，容易出错，所以写了这个脚本把常用操作封装成交互式菜单，生产环境用下来确实省力不少。

脚本集群管理逻辑总览

redis-manage.sh 的主菜单里有三个子菜单对应三种集群模式，功能划分得比较清晰：

主从复制相关的操作都在”集群管理”里，哨兵有独立的”哨兵管理”菜单，Redis Cluster则在”Redis Cluster管理”中。整个脚本的设计思路是：

所有修改操作都会先备份配置文件，万一操作失败能回滚。优先用 CONFIG SET 或 SENTINEL SET 动态改参数，避免重启服务。密码通过环境变量传递，不在命令行暴露。还用了时间戳缓存机制，减少重复检测，菜单响应快一些。关键操作会记日志，方便事后排查。

集群相关函数调用关系：

3.1 Redis主从复制

3.1.1 Redis主从复制架构

Redis主从复制是一主多从的结构，主节点负责写，从节点通过异步复制同步数据并提供读服务。初次连接时主节点会生成RDB快照发给从节点（全量同步），之后写命令实时传播（增量同步）。从节点可以分担读压力，提升吞吐量。

3.1.2 主从复制实现

脚本把主从配置流程自动化了，主要涉及两个核心函数。

（1）配置主节点（cluster_setup_master）

执行时会先检查Redis是否在运行，然后获取当前角色，如果已经是从节点会给出警告。接下来备份配置文件，设置 replica-serve-stale-data = yes，还会提醒用户设置 min-replicas-to-write 和 min-replicas-max-lag 参数——这些参数对保证数据一致性很重要。如果配置文件里有 requirepass，会自动同步设置 masterauth。最后把修改写入配置文件，显示更新项和错误数。

（2）挂载从节点（cluster_add_slave）

执行时先检查Redis运行状态，如果当前已经是从节点，会询问是否强制重新挂载。然后交互输入主节点的IP、端口和密码（可选），先测试连通性，验证主节点身份——如果主节点本身也是从节点，会给出警告。之后备份配置文件，设置 masterauth（如果密码非空）和 replica-read-only = yes，执行 REPLICAOF 命令挂载。挂载成功后会把配置写入文件，等待最多10秒检查同步状态，最后输出结果。

3.1.3 主从复制故障恢复

脚本提供了 cluster_failover 函数来手动切换故障。执行时先检查当前角色，只有从节点才能执行。然后显示当前主节点地址和连接状态，这里会警告脑裂风险——如果旧主节点还在线，贸然切换可能导致数据不一致。确认后执行 REPLICAOF NO ONE 提升为主节点，注释掉配置文件中的 replicaof 行，验证角色变更后给出后续操作建议，比如把旧主节点降级为从节点重新挂载。

3.1.4 实现Redis的级联复制

脚本没有单独封装级联复制的菜单，但可以通过组合操作实现：在中间节点上先执行 cluster_setup_master 优化参数，再执行 cluster_add_slave 挂载到顶级主节点，其他节点再挂载到中间节点就能形成链式复制。不过要注意级联会增加延迟，不建议太长的链。

3.1.5 主从复制优化

脚本内置了一些优化措施：从节点默认设置 replica-read-only yes 防止误写；主节点会提醒配置 min-replicas-to-write 和 min-replicas-max-lag 来保证一致性；repl-backlog-size 建议不小于64MB，脚本没有直接修改，可以手动调整。

3.2 Redis Sentinel 哨兵

3.2.1 为什么需要哨兵

主从复制的问题在于故障发生时需要手动切换，无法自动恢复。生产环境中这个风险太高，所以需要引入哨兵机制。Redis Sentinel提供高可用能力，通过监控主从节点并自动执行故障转移。Sentinel本身也是分布式系统，建议部署奇数个节点（至少3个），这样能保证选举的可靠性。

3.2.2 哨兵Sentinel工作原理

Sentinel的工作流程可以简单概括为四个阶段：监控阶段定期PING节点；单节点判定不可达称为主观下线（SDOWN）；达到quorum数的Sentinel确认后称为客观下线（ODOWN）；之后选举从节点晋升为主节点，更新配置并通知客户端完成故障转移。

3.2.5 应用程序连接Sentinel

应用程序不应直接连接Redis节点，而应通过Sentinel获取当前主节点地址：使用 SENTINEL get-master-addr-by-name 获取主节点，用 SENTINEL slaves 获取从节点列表。主流客户端库如Jedis、Lettuce都支持Sentinel模式，配置哨兵节点列表即可自动处理故障转移。

3.3 Redis Cluster

3.3.1 Redis Cluster介绍

主从+哨兵模式解决了高可用问题，但所有数据都在同一个主节点上，容量和性能受到限制。当单节点无法满足需求时，就需要Redis Cluster来实现数据分片。Cluster支持16384个slot的分片和自动故障转移，采用无中心架构，节点间通过Gossip协议通信。

3.3.2 Redis Cluster架构

数据槽位通过 CRC16(key) % 16384 计算映射；故障检测需要半数以上节点确认主节点不可达才会触发failover；客户端访问时如果key不在当前节点，会收到 MOVED 或 ASK 错误并重定向到正确的节点。

3.3.4 Redis Cluster管理

脚本涵盖了日常运维的主要操作：

重新分片通过 redis_cluster_reshard 函数：输入集群节点和要迁移的槽位数，指定目标节点ID（可选）和源节点ID（可选，all表示所有节点），执行重分片命令并自动确认。

健康检查直接执行 redis-cli --cluster check，输出详细检查结果。

集群修复执行 redis-cli --cluster fix，尝试自动修复常见问题。

3.3.5 Redis Cluster的局限性

Cluster模式虽然强大，但也有一些需要注意的地方：不支持多数据库；批量操作要求所有键在同一槽位（需要使用hash tag）；事务仅限于单槽位；运维相对复杂，不过脚本已经把常用操作自动化了；客户端需要支持集群协议才能正常工作。
