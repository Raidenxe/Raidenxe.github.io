在 Debian 上部署 Jenkins 的完整实战指南（APT + Docker）

从零搭建 CI/CD 环境，踩坑记录与解决方案全公开

作者：raiden
测试环境：Debian 13 (Trixie) / Jenkins LTS 2.541.1 / Docker 29.7.2
最后更新：2026-08-09

1. 为什么选择 Jenkins？部署方式怎么选？

Jenkins 是目前最成熟的开源自动化服务器，拥有超过 1800 个插件，几乎可以对接任何主流开发工具链。但在 Debian 上部署时，很多人会遇到仓库签名失败、Docker 镜像拉取报错、容器重启后退出、初始密码丢失等一系列问题。

本文提供 APT 和 Docker 两种部署方案的完整操作流程，并重点剖析官方文档未覆盖的”暗坑”。笔者使用的系统是 Debian Trixie (Testing)，遇到的兼容性问题极具代表性，相信对多数读者都有参考价值。

两种部署方式对比

维度 APT（系统包） Docker（容器化）
优点 与 systemd 深度集成，服务管理方便 环境隔离，版本切换灵活，迁移友好
缺点 依赖系统版本，Testing 分支可能无预编译包 需额外管理容器生命周期与数据卷
适用场景 生产环境、长期维护 测试环境、快速验证、多版本共存

2. 方案一：APT 方式部署（适合稳定生产）

2.1 安装 Java 运行时（必须前置）

Jenkins 基于 Java 开发，运行前必须安装 JRE/JDK。自 2025 年 12 月起，Jenkins 要求 Java 17 或 21，推荐 OpenJDK 21 [citation:10][citation:16]。

注意：若系统同时安装了多个 Java 版本，使用 sudo update-alternatives --config java 切换至 Java 21。

2.2 添加 Jenkins 官方 APT 仓库

这是最容易出错的环节。很多人执行 apt install jenkins 后提示”没有可用的软件包”，根源就在于仓库未正确添加 [citation:7]。

关键变更（2025.12 起生效）：Jenkins 更换了 Linux 仓库签名密钥，新密钥文件名为 jenkins.io-2026.key，旧版 jenkins.io-2023.key 仍可用于旧版本，但安装最新 LTS 必须导入新密钥 [citation:13]。

排错要点：

  • 若 apt update 输出中看不到 Jenkins 源，检查 /etc/apt/sources.list.d/jenkins.list 是否存在且内容正确。
  • 文件缺失通常是因为 tee 命令前未加 sudo，导致写入失败却无报错。
  • 若仍报错 NO_PUBKEY，确认密钥环路径与源文件中 signed-by= 完全一致 [citation:13][citation:16]。

Weekly 版本用户：将上面的 debian-stable 替换为 debian，密钥也对应使用 jenkins.io-2026.key（weekly 地址）[citation:13]。

2.3 安装 Jenkins

安装完成后，包管理器会自动完成以下操作 [citation:16][citation:19]：

  • 创建 jenkins 系统用户
  • 设置 /var/lib/jenkins 为工作目录（JENKINS_HOME）
  • 注册 systemd 服务单元
  • 默认监听 8080 端口

2.5 初始化配置

浏览器访问 http://服务器IP:8080，按向导完成以下步骤 [citation:16]：

  1. 解锁 Jenkins：获取初始密码

    复制输出的随机字符串粘贴到网页中。

  2. 安装插件：选择 “Install suggested plugins”（推荐插件），等待 5~10 分钟。

  3. 创建管理员用户：务必填写用户名和密码，不要跳过此步骤——依赖初始密码在生产环境是安全风险 [citation:16]。

  4. 确认 Jenkins URL：填写实际访问地址（如配置了反向代理则填域名）。

2.6 APT 方式常见问题排查

问题 1：apt install jenkins 提示”没有可用的软件包”

  • 原因 A：仓库未成功添加，回到 2.2 节逐步检查。
  • 原因 B：Debian Testing (Trixie) 官方仓库可能尚未提供预编译包 [citation:7]。
  • 解决方案：改用 Docker 方式（见第三节），或直接下载 WAR 包运行：java -jar jenkins.war --httpPort=8080 [citation:19]。

问题 2：安装插件后重启，服务起不来

  • 常见原因是 Java 版本过低，升级至 Java 17+ 后重试 [citation:10]。

3. 方案二：Docker 方式部署（推荐新手 / 测试环境）

Docker 方式可以彻底规避系统版本兼容性问题，环境隔离干净，适合快速搭建和迁移 [citation:5]。

3.3 运行容器（含重启策略）

关键参数解析：

参数 作用 说明
--restart=on-failure 非正常退出时自动重启 核心参数，解决容器安装插件后 Exited 5 的问题 [citation:5][citation:8]
-p 8080:8080 Web 界面端口 可改为 -p 9090:8080 避免端口冲突
-p 50000:50000 Agent 通信端口 无自建 Agent 需求可不映射
-v jenkins_home:... 数据持久化 使用命名卷，容器删除后数据不丢失
-e JAVA_OPTS JVM 内存限制 低配服务器务必设置，防止 OOM

关于 --restart=on-failure 的官方说明：自 Jenkins 2.344（2022-04）起，控制器镜像的退出/重启行为已变更。Jenkins 升级插件或手动重启时不再使用 exec() 自重启，而是主动退出（exit code 非 0），交由 Docker 守护进程拉起。因此 必须设置重启策略，否则容器会”假死”退出 [citation:5]。

3.4 获取初始密码

后续 Web 初始化流程与 APT 方式一致（安装插件 → 创建管理员 → 确认 URL）。

3.5 Docker 方式常见问题排查

问题 1：docker pull jenkins 报错 failed size validation

  • 原因：旧镜像 jenkins（无命名空间）已损坏或废弃。
  • 解决：改用 jenkins/jenkins:lts [citation:11]。

问题 2：容器启动后很快退出，状态显示 Exited (5)

  • 原因：Jenkins 内部触发重启（如插件安装后），主动退出但外部无重启策略。
  • 解决： 无需重建容器，docker update 可热更新重启策略 [citation:5][citation:20]。

问题 3：重启策略应该用 on-failure 还是 always？

策略 行为 适用场景
no 永不重启（默认） 调试阶段
on-failure[:N] 仅异常退出时重启，可限次数 Jenkins 官方推荐 [citation:5]
always 任何情况都重启（含正常退出） 纯 Web 服务
unless-stopped 类似 always，但手动 stop 后不再自动拉起 需手动控制生命周期

**推荐 on-failure**：Jenkins 的正常退出码为 0（如手动 stop），此时不需要重启；异常退出码非 0 时才需要 Docker 介入 [citation:17][citation:20]。

5. 部署后的最佳实践

5.1 版本策略

  • 生产环境：始终使用 lts 标签，稳定性优先，避免 Weekly 版本的频繁变更风险 [citation:10]。
  • 测试环境：可尝试 Weekly 版本体验新特性，当前 Weekly 版本已迭代至 2.549+ [citation:10]。

5.2 数据持久化

部署方式 数据位置 备份命令
APT /var/lib/jenkins/ sudo tar czf jenkins-backup.tar.gz /var/lib/jenkins/
Docker 命名卷 jenkins_home docker run --rm -v jenkins_home:/data -v $(pwd):/backup busybox tar czf /backup/jenkins-backup.tar.gz /data

核心原则：JENKINS_HOME 包含所有作业配置、构建历史、插件和用户凭据，是灾难恢复的唯一关键数据 [citation:6]。

5.3 配置国内镜像加速插件下载

官方插件源在国内访问较慢，建议替换为清华镜像 [citation:7]：

  1. 进入 Manage Jenkins → Plugins → Advanced settings
  2. 将 Update Site 替换为：https://mirrors.tuna.tsinghua.edu.cn/jenkins/updates/update-center.json
  3. 保存后点击 Check now 验证连通性

5.4 反向代理与 HTTPS

生产环境建议前置 Nginx/Caddy 反向代理，实现：

  • 域名访问（替代 IP:端口）
  • TLS 加密（Let’s Encrypt 免费证书）
  • 静态资源缓存加速

5.5 安全加固清单

  • 修改默认 8080 端口（Docker 映射 -p 9090:8080，APT 修改 /etc/default/jenkins 中 JENKINS_PORT）
  • 禁用匿名用户访问
  • 启用 CSRF 保护（默认开启）
  • 定期更新插件和 Jenkins 核心版本
  • 配置定期备份策略（cron + 异地存储）

6. 总结

部署方式 成功关键点 典型坑位
APT 正确导入 2026 版 GPG 密钥；Java 21 前置安装 Debian Testing 无预编译包；插件不兼容导致启动失败
Docker 使用 jenkins/jenkins:lts 镜像；设置 --restart=on-failure 误用废弃的 jenkins 镜像；容器 Exited 5 后不自动恢复
密码重置 修改 config.xml 禁用安全 → 重置 → 重新启用 忘记停止服务就修改配置导致不生效

希望这篇指南能帮你避开我从 Debian Buster 到 Trixie 一路踩过来的所有坑，顺利在 Debian 上跑起 Jenkins CI/CD 流水线。
