MySQL 8.0 三节点 MGR（Group Replication）高可用集群部署

本文基于一次真实部署整理：在一台服务器上用 Docker Compose 起三个 MySQL 8.0 容器，组成单主模式（Single-Primary）的 MGR 组复制高可用集群，并实际验证了主写从读一致、从节点只读约束、集群恢复。

一、方案选型：为什么是 MGR

高可用数据库方案常见有 主从复制（异步/半同步）、MHA、MGR：

方案 强一致性 自动故障切换 复杂度 说明
主从 + MHA 弱（异步可能丢数据） 需外部组件 中 经典，MHA 作为协调器
半同步复制 中 需外部组件 中 semi_sync 减少丢数据
MGR（本方案） 强（组内多数派确认） 原生，秒级 中高 基于 Paxos，自带故障转移

MGR（MySQL Group Replication）把每个节点的 binlog 广播给组内所有成员，任一成员缺失事务会在线回放到最新，从而在组内实现多数派一致的复制，且主节点故障后组内自动推选新主，无需额外协调组件。

二、MGR 技术原理

理解了”它能做什么”，再看它内部怎么工作，部署时踩坑就有据可依了。

2.1 本质：基于 Paxos 的多主状态机复制

MGR 并不是”主从同步的加强版”，而是用 Paxos 一致性协议 + 组通信（GCS）实现的状态机复制。每个节点独立运行业务产生事务，但事务要在组内经过认证（Certification）达成全局一致后才被应用。

与传统异步主从的根本差异：

传统主从（MySQL Replication） MGR
事务来源 只有主节点产生 各成员均可产生（单主模式下写路由到主）
分发方式 主节点 SQL 线程单点下推 组内广播 + 多数派共识排序
一致性 异步，可能有延迟/丢 强一致（组内多数派确认）
故障转移 靠 MHA 等外部协调器 协议内置，自动选主

2.2 分层架构

MGR 内部主要由两类组件协作：

  • 认证 / 复制模块（Certification / Applier）：负责全局事务协调、write-set 冲突检测、事务的分发与应用。
  • 组成员服务（GCS）与 Paxos 通信层：负责成员间心跳、状态广播、事务全序排序、成员视图管理。

两者共同回答了 MGR 面对的两个核心问题：

  1. 事务顺序：组内任意两个事务谁先谁后——由 Paxos 决定的全序保证。
  2. 成员集合：谁在线、谁掉线、谁是新主——由 GCS 成员服务产生视图。

2.3 单主模式下一条写事务的生命周期

客户端只写 PRIMARY：

  1. PRIMARY 执行事务，先落本地 binlog；
  2. 事务被广播给组内所有成员，并用 transaction_write_set_extraction=XXHASH64 生成基于行的写集（write-set）作为冲突标记；
  3. 组内通过 Paxos 对事务达成一致顺序；
  4. 各成员在认证阶段用 write-set 做冲突检测——单主模式写只来自主，基本无冲突，认证主要保证”顺序一致、各成员不重复应用”；
  5. 通过认证后，事务在各成员本地按同一顺序应用：SECONDARY 把事务写入 relay log，并经 group_replication_applier 应用，从而与 PRIMARY 保持一致。

2.4 单主模式：写路由与从节点只读

  • group_replication_single_primary_mode=ON 时，同一时刻只有一个 PRIMARY 可写，其余 SECONDARY 会被组复制自动设为 super_read_only。
  • 这正是我们后面实测到从节点 INSERT 被 --super-read-only 拒绝的原因。
  • 客户端不能自行猜测主节点，需要通过 MySQL Router / 探活等方式定位当前 PRIMARY。

2.5 一致性级别：group_replication_consistency

该参数决定读写事务在返回给客户端前，期望多少个成员已确认：

取值 含义
EVENTUAL 最终一致，事务应用到本机即返回
AFTER（默认 / 本文采用） 事务在本机执行完成、准备提交时才返回
AFTER_WAIT 等待所有在线成员已应用中才返回（更慢但更稳）

注意：AFTER_WRITE 是无效取值，会导致 mysqld 频繁重启失败（见踩坑 10.1）。稳定可靠取 AFTER。

2.6 故障转移与多数派（quorum）

MGR 基于 Paxos，任何决策都需要组内多数派：

  • PRIMARY 故障：其余成员通过 GCS 检测到视图变化，只要多数派在线就选出新 PRIMARY，业务几乎无感（秒级）。
  • 网络分区防护：当成员被分裂成无法各自形成多数派的两部分时，少数派会自动下线/停止服务，从根本杜绝”脑裂多主”。group_replication_exit_state_action=ABORT_SERVER 可让脱离节点的进程主动退出，避免写脏数据。
  • 三节点组成的多数派是 2，最多容忍 1 台故障；若想容忍 2 台故障需 5 节点。

2.7 GTID、recovery 通道与在线回放

  • 每个成功事务都带一个全局唯一的 GTID；组内以 gtid_executed 集合跟踪”每个成员执行到哪”。
  • 新节点加入时，通过专门的 group_replication_recovery 通道 连上组内某成员 repl 账号，把自身缺失的 GTID 对应事务在线回放到最新，再转由应用通道追平。
  • 这也解释了为什么节点加入前不能自带分叉的本地 GTID（见踩坑 10.2）：本地产生的、组内不存在的 GTID 会让节点无法以干净基线加入。

九、方式二（官方更推荐）：用 MySQL Shell (AdminAPI) 接管

mysql 客户端 + SQL 是「底层手段」，而 MySQL Shell 的 AdminAPI 是官方推荐的高层管理方式：它把 Group Replication 的创建、扩缩容、故障切换、添加账号等操作封装成 dba.cluster 一系列现成方法，自动处理插件加载、服务器变量、元数据（mysql_innodb_cluster_metadata），心智负担更低，也适合脚本化运维。官方建议生产上用 InnoDB Cluster + MySQL Shell 管理。

方式一和方式二不冲突：前者用于「手工演示底层原理」，后者是「更省心的生产方式」。二者都能管理同一个 GR 组。

十一、踩坑记录（重点）

11.1 容器反复重启，报 Error while setting value ... to group_replication_consistency

  • 原因：group_replication_consistency 取值为无效的 AFTER_WRITE。
  • 修复：改回合法值 AFTER（或 AFTER_WAIT / EVENTUAL 等）。正是它导致节点启动循环失败。

11.2 加入节点报 This member has more executed transactions than those present in the group

  • 原因：节点加入前本机已产生组内不存在的本地事务——典型是每个节点都执行了初始化 SQL，各自生成了自己的 GTID。
  • 正确做法：初始化 SQL（建账号/建库）只允许 seed 节点执行（Compose 里仅 mysql0 挂载 node_init.sql）。
  • 若已发生：在问题节点执行 RESET MASTER; START GROUP_REPLICATION; 清空本地 GTID 后再加入。

11.3 recovery 通道连接成功但 COM_REGISTER_REPLICA failed: Access denied for user 'repl'@'%'

  • 原因：repl 账号存在但只有 USAGE 权限（多行 GRANT 在 initdb 阶段解析中断，只建了用户没授权）。
  • 修复：补齐权限后再加入：
  • 防范：把每个 SQL 语句写成一整行，勿用跨行 GRANT 后再挂载。

11.4 unknown variable 'loose-group_replication_*'

  • 原因：组复制插件未加载（官方镜像默认不自动加载 .so）。
  • 修复：运行时 INSTALL PLUGIN group_replication SONAME 'group_replication.so' 加载后，SET GLOBAL group_replication_* 才生效（mgr-init.sh 已自动处理）。

11.5 server_id = 0 不合法

  • 组复制要求有效且唯一的 server_id。三节点设为 1 / 2 / 3。

11.6 用 MySQL Shell（方式二）时可能遇到的问题

  • mysql:8.0 镜像没有 mysqlsh：需要 mysql/mysql-server:8.0（内置 MySQL Shell）；或单独额外安装。用独立 mgr-shell 容器管理更干净。
  • adoptFromGr 需服务器满足 AdminAPI 配置：若 checkInstanceConfiguration 报出待修复项（如未启用并行复制并行应用），用 dba.configureInstance(...) 自动修正并持久化后再接管。
  • 管理账号：生产不建议长期用明文 root 管理集群，用 cluster.setupAdminAccount('icadmin') 建专用账号。
  • 接管后不要再手动改服务器变量：一旦纳入 InnoDB Cluster，应统一用 AdminAPI 维护 Group Replication 配置，避免与元数据不一致。

十二、结语

本文用一个真实跑通的案例，完整走通了 Docker Compose 部署 MySQL 8.0 MGR 单主集群：

  • ✅ 三节点 ONLINE，单主模式
  • ✅ 主写从读实时一致
  • ✅ 从节点只读约束生效，防多主脑裂
  • ✅ 集群可一键幂等恢复

同时，如果你想更省心，可以采用上一章介绍的方式二：用 MySQL Shell 的 dba.createCluster({adoptFromGr:true}) 一条命令把现有组纳入 InnoDB Cluster 管理，官方更推荐这种方式。

生产环境建议：

  • 密码改用环境变量 / Secret 管理，MYSQL_ROOT_PASSWORD 不要明文写死在 Compose。
  • 将 data/、logs/ 纳入定期备份与监控。
  • 用 mgr-status.sh 定期巡检成员健康，结合告警（如 Prometheus mysql_* / 脚本轮询）。

若要用在跨主机 / 生产多机场景，把 report_host、local_address 换成各节点真实网卡 IP，并放开 3306/33061 防火墙即可，原理完全一致。
