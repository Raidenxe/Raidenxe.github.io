实验一：CoreDNS 部署与内部服务解析

1.1 CoreDNS 组件概述

CoreDNS 是 Kubernetes 的默认 DNS 组件，负责集群内部的服务发现和域名解析。它通过监听 Kubernetes API Server 的 Service 和 Pod 变化，动态生成 DNS 记录。

CoreDNS 的核心功能：

  • 服务发现：将 Service 名称解析为 ClusterIP 或 Pod IP
  • Pod 解析：支持将 Pod IP 反向解析为 DNS 名称
  • 外部 DNS 转发：将集群外部的域名请求转发到上游 DNS 服务器

1.3 CoreDNS 工作原理分析

1.3.1 DNS 记录生成规则

CoreDNS 通过 kubernetes 插件监听 Kubernetes API Server，自动为 Service 和 Pod 生成 DNS 记录。

Service DNS 记录格式：

记录类型 格式 示例
ClusterIP Service <service>.<namespace>.svc.cluster.local mysql.m68.svc.cluster.local → 10.105.163.57
Headless Service <service>.<namespace>.svc.cluster.local mysql-headless.m68.svc.cluster.local → 10.244.0.21 (Pod IP)
ExternalName Service <service>.<namespace>.svc.cluster.local 返回 CNAME 记录
Pod <pod-ip>.<namespace>.pod.cluster.local 10-244-0-21.m68.pod.cluster.local

域名规范说明：

  • svc：Service 记录子域
  • cluster.local：集群域名（可通过 --cluster-domain 配置）
  • 短名称解析：Pod 可通过 <service> 直接访问同一 Namespace 下的 Service

实验二：Ingress Nginx 控制器部署与高级路由

2.1 Ingress Nginx 控制器概述

Ingress Nginx 是 Kubernetes 官方维护的 Ingress 控制器实现，基于 NGINX 反向代理，提供 HTTP/HTTPS 路由功能。

核心功能：

  • 基于 URL 路径的路由：根据请求路径分发到不同后端服务
  • 基于主机名的路由：根据 Host 头分发到不同后端服务
  • TLS/SSL 终止：支持 HTTPS 证书配置
  • 蓝绿发布：通过 Service 选择器切换实现流量控制
  • 灰度发布：通过权重或请求头实现精细流量切分

实验三：灰度发布（金丝雀发布）实验

3.1 灰度发布原理

灰度发布（Canary Release）是一种比蓝绿发布更渐进、更安全的发布策略。它通过将一小部分用户流量（例如 10%）引导至新版本（金丝雀版本），在生产环境中进行真实流量验证。如果新版本运行稳定且无异常，再逐步增加流量比例，直至全部切换；若发现问题，可立即将流量切回旧版本。

与蓝绿发布的区别：

  • 蓝绿发布：瞬间切换全部流量，适合对停机时间要求极高的场景，但回滚也是全量。
  • 灰度发布：逐步迁移流量，风险更低，可以在线监控新版本的性能与错误率，但发布周期更长。

3.2 Ingress-Nginx 的 Canary 机制

Ingress-Nginx 控制器原生支持灰度发布，通过在 Ingress 资源上添加特定的 annotation（注解） 来实现。核心注解如下：

注解 说明 可选值
nginx.ingress.kubernetes.io/canary 开启灰度发布 "true"
nginx.ingress.kubernetes.io/canary-weight 基于权重的流量比例 0 - 100 的整数
nginx.ingress.kubernetes.io/canary-by-header 基于请求头的灰度（如 X-Canary: always） 自定义 Header 名称
nginx.ingress.kubernetes.io/canary-by-cookie 基于 Cookie 的灰度（如 canary=always） 自定义 Cookie 名称

优先级： canary-by-header > canary-by-cookie > canary-weight

实验总结

CoreDNS 实验总结

  1. CoreDNS 自动为所有 Service 生成 DNS 记录，包括 ClusterIP 和 Headless 类型
  2. ClusterIP Service 解析返回 ClusterIP，由 kube-proxy 实现负载均衡
  3. Headless Service 解析直接返回 Pod IP，适用于需要直接访问 Pod 的场景
  4. 短名称解析通过 /etc/resolv.conf 中的 search 域自动补全
  5. 外部域名解析通过 CoreDNS 的 forward 插件转发到上游 DNS
  6. 宿主机映射通过 Corefile 的 hosts 插件实现

Ingress Nginx 实验总结

  1. Ingress 控制器通过 Service NodePort 暴露，宿主机通过 192.168.39.112:30080 访问
  2. 基于 URL 路径的路由通过 rewrite-target 注解实现路径重写，后端服务无需感知子路径
  3. 蓝绿发布通过修改 Service 的 selector 实现流量切换，即时生效（需等待控制器缓存更新）
  4. 灰度发布通过 Canary Ingress 注解实现精细流量控制，支持权重、Header、Cookie 三种模式
  5. 灰度升级流程：10% → 50% → 100%，逐步验证新版本稳定性后再全量切换
  6. Ingress 控制器监听 IngressClass，通过 ingressClassName: nginx 关联
  7. RBAC 权限需包含 leases 资源（coordination.k8s.io）以支持领导者选举

灰度发布 vs 蓝绿发布对比

特性 蓝绿发布 灰度发布
切换速度 瞬间全量 逐步增量
风险等级 较高（全量切换失败影响所有用户） 低（仅影响小部分用户）
回滚速度 快（瞬间切回） 快（降低权重或直接切回）
真实流量验证 无法在线验证 可以用小流量在线验证
流量控制粒度 粗粒度（全有或全无） 细粒度（百分比/Header/Cookie）
适用场景 紧急修复、无状态应用 重大版本更新、需要长期观察

关键技术点

技术点 说明
DNS 解析流程 Pod → resolv.conf → CoreDNS → API Server → 返回记录
Service 类型影响 ClusterIP 返回虚拟 IP，Headless 返回 Pod IP
Ingress 路由 基于 Host + Path 分发到不同后端 Service
蓝绿切换 修改 Service selector 即时切换，保留旧版本用于回滚
灰度权重 canary-weight 控制流量比例，0-100 整数
灰度 Header canary-by-header 定向放行特定请求到新版本
灰度 Cookie canary-by-cookie 按用户会话保持版本一致性
路径重写 rewrite-target 注解去除前缀路径
金丝雀 Ingress 与主 Ingress 共享 Host，通过注解开启灰度

注意事项

  • 金丝雀 Ingress 必须与主 Ingress 的 host 完全一致
  • 金丝雀 Ingress 不需要包含主 Ingress 的所有路径规则，只需定义需要灰度的路径即可
  • 多个金丝雀 Ingress 可以共存，但权重会叠加计算
  • 基于 Header/Cookie 的灰度优先级高于权重，适合 QA 或内部测试团队定向验证
  • 灰度期间旧版本 Pod 必须保持运行，不可提前删除
  • 全量切换后应及时清理金丝雀 Ingress 和 Service 资源，避免遗留配置
  • canary-weight: 0 不等于删除金丝雀 Ingress，流量仍可能被 Header/Cookie 规则命中
