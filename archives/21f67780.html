Kubernetes 集群部署：从原理到实践

环境：Ubuntu 26.04 LTS / Kubernetes v1.36.2 / containerd + cri-dockerd

一、Kubernetes 集群部署架构概述

1.1 kubeadm 的作用与原理

kubeadm 是 Kubernetes 官方提供的集群部署工具，它的核心任务是将一个 Kubernetes 集群的各个组件以容器化的方式部署到目标机器上。kubeadm 的工作原理可以概括为三个阶段：

  1. 前置检查：kubeadm init 执行前会进行一系列预检，包括主机名解析、端口占用、CRI 端点可用性、Swap 状态等。任何一项不通过都会阻止初始化。
  2. 组件启动：以静态 Pod 的方式启动 kube-apiserver、kube-controller-manager、kube-scheduler、etcd 等控制平面组件。这些组件的 YAML 清单由 kubeadm 生成并放置在 /etc/kubernetes/manifests/ 目录下，kubelet 会监听该目录并自动启动对应的容器。
  3. 集群引导：生成证书、kubeconfig 文件、RBAC 规则等集群基础设施，并为后续的工作节点加入提供令牌（token）。

1.2 kubelet 与控制平面的交互


kubelet 是集群中每个节点上运行的代理组件，它通过 CRI（Container Runtime Interface）与容器运行时通信，负责管理 Pod 的生命周期。kubelet 与控制平面组件的交互流程如下：

kubelet 启动时通过 kubeconfig 文件中的证书信息向 kube-apiserver 注册节点信息，之后通过 Watch 机制监听 apiserver 上分配给本节点的 Pod 变更，并据此创建或销毁容器。

1.3 CRI 与容器运行时的关系

CRI（Container Runtime Interface）是 Kubernetes 定义的一组 gRPC 接口，用于解耦 kubelet 与具体的容器运行时实现。常见的容器运行时和对应的 CRI 实现包括：

容器运行时 CRI 实现 通信方式
containerd 内置 CRI 插件 /var/run/containerd/containerd.sock
Docker cri-dockerd（适配器） /var/run/cri-dockerd.sock
CRI-O 原生 CRI 实现 /var/run/crio/crio.sock

kubelet 通过 Unix Socket 与 CRI 端点通信，因此当系统中存在多个 CRI 端点时，kubeadm 必须通过 --cri-socket 参数明确指定使用哪一个。

2.2 容器运行时 cgroup 驱动原理

Linux 的 cgroup（Control Group）是容器资源隔离的基础。Kubernetes 集群中，kubelet 和容器运行时（containerd）各有一套 cgroup 驱动机制，两者必须保持一致。

两种 cgroup 驱动：

systemd 通过 systemd 的 cgroup 管理接口 使用 systemd 作为 init 系统的 Linux 发行版

三、集群高可用架构设计

3.1 高可用架构整体设计

生产环境中，Kubernetes 控制平面的高可用是保障集群稳定运行的关键。单控制节点部署存在单点故障风险——一旦该节点宕机，整个集群将无法管理。高可用架构的核心思想是：部署多个控制平面节点，并通过负载均衡器将 API 请求分发到所有可用的控制节点。

3.2 各组件角色与关系

3.2.1 负载均衡层：HAProxy 与 Nginx

HAProxy 和 Nginx 均支持四层（TCP）负载均衡，能够将客户端请求分发到后端的多个 kube-apiserver 实例。

组件 工作模式 配置复杂度 适用场景
HAProxy 原生四层代理，配置简洁 低 专用于负载均衡，推荐用于 K8s API 场景
Nginx 需配置 stream 模块实现四层代理 中 已使用 Nginx 的团队，统一管理负担

HAProxy 的核心优势在于：

  • 配置语义清晰，对四层负载均衡的支持更加原生
  • 内置简洁的状态监控页面（/status），便于运维人员实时观察后端各节点的健康状态
  • 支持精细的健康检查参数（间隔、失败阈值、恢复阈值）

Nginx 的优势在于：

  • 已经在使用 Nginx 的团队可以统一管理，减少运维组件数量
  • 通过 stream 模块实现四层代理，与 HTTP 配置分离管理

3.2.2 高可用保障层：Keepalived

Keepalived 通过 VRRP（Virtual Router Redundancy Protocol）协议实现虚拟 IP（VIP）的漂移，确保负载均衡器本身的高可用。其核心机制如下：

  • 主备两台 HAProxy 节点上各运行一个 Keepalived 实例
  • 主节点（MASTER）持有 VIP，处理所有 API 请求
  • Keepalived 通过 VRRP 通告报文进行心跳检测，监控主节点状态
  • 当主节点故障时，备节点（BACKUP）自动接管 VIP，整个过程对客户端透明
  • 通过 vrrp_script 机制监控 HAProxy 进程状态，当 HAProxy 异常时主动降级触发切换

3.2.3 控制平面层：多 Master 节点

多个控制平面节点各自运行完整的 kube-apiserver、kube-controller-manager、kube-scheduler 和 etcd 组件。其中：

  • kube-apiserver 是无状态的服务，可以水平扩展，通过负载均衡器统一对外提供服务
  • etcd 采用 Raft 协议实现分布式一致性，奇数个节点（3 或 5）确保选主能正常达成多数派
  • kube-controller-manager 和 kube-scheduler 通过 --leader-elect 参数实现领导者选举，同一时刻只有一个实例处于活跃状态

关键机制说明：

  1. 客户端无感知：客户端始终通过 VIP 访问，无需感知后端节点的变化或故障切换
  2. 健康检查自动剔除：HAProxy 定期对后端 kube-apiserver 进行健康检查（check inter 3s fall 3 rise 3），自动将故障节点从负载池中移除
  3. 双重高可用保障：Keepalived 的 vrrp_script 监控 HAProxy 进程，HAProxy 的健康检查监控 kube-apiserver 进程，构成两层故障检测机制
  4. 控制节点通过 VIP 加入：额外的控制平面节点加入集群时，同样通过 VIP 与 kube-apiserver 通信，规避了单个 Master 节点的故障风险

五、kubeconfig 认证原理与 CNI 网络插件

5.1 kubeconfig 认证原理


kubectl 通过 kubeconfig 文件中的凭证信息向 kube-apiserver 发起认证请求。kubeconfig 文件包含以下关键信息：

  • clusters：集群的 API Server 地址和 CA 证书
  • users：客户端证书或 token
  • contexts：将用户与集群关联起来

kubeadm init 成功后生成的 /etc/kubernetes/admin.conf 包含完整的集群凭证。kubectl 默认从 $HOME/.kube/config 加载 kubeconfig 文件。如果该文件不存在或不可读，kubectl 会回退到默认的 localhost:8080 非安全端口连接，导致连接拒绝。

5.2 CNI 网络插件原理


Kubernetes 集群中的 Pod 网络需要由 CNI（Container Network Interface）插件实现。kubeadm 本身不提供网络解决方案，因此初始化完成后节点处于 NotReady 状态是正常现象，kubelet 日志中会显示：

CNI 插件的核心功能包括：

  • Pod IP 分配：为每个 Pod 分配一个集群内唯一的 IP 地址
  • 跨节点通信：确保不同节点上的 Pod 可以互相通信
  • 网络策略：部分 CNI 插件支持 NetworkPolicy 定义 Pod 间访问规则

常用 CNI 插件对比：

插件 特点 适用场景
Flannel 简单、使用 VXLAN 或 host-gw 封装 初学者、小规模集群
Calico 支持 BGP 和 NetworkPolicy 生产环境、需要网络策略
Cilium 基于 eBPF，性能优异 高级网络场景

六、Kubernetes 常见资源及作用

Kubernetes 通过声明式 API 管理各种资源对象，理解这些资源的作用和关系是使用 Kubernetes 的基础。

6.1 资源分类与层次关系

6.2 核心资源详解

6.2.1 Pod

作用：Kubernetes 最小的部署单元，是一组共享网络和存储的容器集合。

特点：

  • 多个容器共享同一个网络命名空间（共享 IP 和端口）
  • 共享存储卷
  • 作为一个整体被调度到同一个节点

典型场景：

  • 运行单个应用容器
  • 运行主容器 + 边车（Sidecar）容器（如日志收集、监控代理）

6.2.2 Deployment

作用：管理无状态应用的部署和滚动更新。

特点：

  • 声明式定义期望的 Pod 副本数
  • 支持滚动更新和回滚
  • 自动修复失败的 Pod（自愈能力）

典型场景：

  • Web 服务、API 服务等无状态应用
  • 需要频繁发布更新的应用

6.2.3 StatefulSet

作用：管理有状态应用，保证 Pod 的有序性和唯一性。

特点：

  • Pod 名称带有固定序号（如 mysql-0, mysql-1, mysql-2）
  • 每个 Pod 有稳定的网络标识和持久存储
  • 按顺序创建、更新、删除 Pod

典型场景：

  • 数据库集群（MySQL、PostgreSQL）
  • 需要持久化状态的分布式应用

6.2.4 DaemonSet

作用：确保每个（或部分）节点上运行一个 Pod 副本。

特点：

  • 自动在新加入的节点上部署 Pod
  • 适用于系统级守护进程

典型场景：

  • 日志收集器（Fluentd、Filebeat）
  • 监控代理（Prometheus Node Exporter）
  • 网络插件（Calico、Flannel）

6.2.5 Job / CronJob

作用：执行一次性或定时任务。

特点：

  • Job：执行一次后结束
  • CronJob：按 Cron 表达式定时执行

典型场景：

  • 数据备份
  • 定时清理任务
  • 批处理作业

6.2.6 Service

作用：为 Pod 提供稳定的网络访问入口。

类型：

类型 说明 适用场景
ClusterIP 默认类型，仅集群内部访问 内部服务间通信
NodePort 通过节点端口暴露到集群外部 开发环境、测试环境
LoadBalancer 云平台自动创建负载均衡器 生产环境对外服务
ExternalName 将服务映射到外部域名 访问外部服务

特点：

  • 提供稳定的 ClusterIP，不受 Pod 变化影响
  • 自动负载均衡到后端 Pod
  • 通过标签选择器关联 Pod

6.2.7 Ingress

作用：管理 HTTP/HTTPS 流量的路由规则。

特点：

  • 支持基于域名的路由
  • 支持路径路由
  • 支持 TLS 终止

典型场景：

  • 多个服务共享同一个域名
  • HTTPS 证书管理

6.2.8 ConfigMap

作用：存储非敏感配置信息。

特点：

  • 以键值对形式存储
  • 可以通过环境变量或文件挂载方式注入 Pod

典型场景：

  • 应用配置文件
  • 环境变量配置

6.2.9 Secret

作用：存储敏感信息（密码、密钥、证书等）。

特点：

  • 数据进行 Base64 编码（注意：不是加密）
  • 支持多种类型（generic、tls、docker-registry）

典型场景：

  • 数据库密码
  • API 密钥
  • TLS 证书

6.2.10 PV / PVC

作用：管理持久化存储。

关系：

  • PV（PersistentVolume）：集群级别的存储资源
  • PVC（PersistentVolumeClaim）：用户对存储资源的申请

典型场景：

  • 数据库持久化存储
  • 需要持久化的应用数据

6.2.11 StorageClass

作用：动态创建 PV。

特点：

  • 用户无需手动创建 PV
  • 根据 PVC 的请求自动创建对应规格的 PV

典型场景：

  • 云平台存储（AWS EBS、Azure Disk、GCP Persistent Disk）
  • 本地存储

9.2 关键教训

命名一致性至关重要

主机名、/etc/hosts 记录、--control-plane-endpoint 参数三者必须保持一致。不一致会导致主机名解析失败，kubelet 无法正确注册到集群。

最佳实践：在创建虚拟机时就确定好主机名，并在 /etc/hosts 中保持完全一致。

cgroup 驱动一致性

containerd 安装后默认不会创建 /etc/containerd/config.toml，需要使用 containerd config default 命令生成默认配置，然后修改 SystemdCgroup = true 与 kubelet 保持一致。

多 CRI 端点环境需要明确指定

当系统中同时存在 containerd 和 cri-dockerd 时，kubeadm 无法自动选择 CRI 端点，必须通过 --cri-socket 参数明确指定。推荐使用 containerd 原生 CRI，性能更优。

9.3 高可用部署注意事项

  1. VIP 配置：--control-plane-endpoint 必须指向 VIP 地址，不能使用单个 Master 的 IP
  2. 证书同步：使用 --upload-certs 参数自动分发证书，避免手动复制
  3. etcd 节点数：控制平面节点数应为奇数（3 或 5），以保证 Raft 协议的多数派选举
  4. 负载均衡器健康检查：确保 HAProxy 的 check 参数正确配置，能及时剔除故障节点
  5. 网络策略：生产环境建议使用 Calico 等支持 NetworkPolicy 的 CNI 插件
