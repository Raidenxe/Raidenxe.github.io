1. 什么是 Bocker

Bocker 是一个用 约 100 行 Bash 脚本 实现的极简容器运行时，由英国系统工程师 Peter Wilmott 创建。它并非用于生产环境，而是通过最精简的代码，揭示 Docker 等容器技术的核心本质——利用 Linux 内核的命名空间（Namespaces）、控制组（Cgroups）、Btrfs 文件系统、veth pair 等特性，组合出一个隔离的执行环境。

项目地址：p8952/bocker（已归档）

3. 源码逐层深度解析

3.1 脚本头部与环境准备

逐行解析

代码 作用 原理
set -o errexit 命令失败时立即退出（set -e） 防止错误累积，但需注意管道和子shell的边界
set -o nounset 使用未定义变量时报错（set -u） 避免拼写错误导致的静默bug
set -o pipefail 管道中任一命令失败则整体失败 默认行为只检查最后一个命令，`cmd1
shopt -s nullglob 通配符无匹配时展开为空字符串 默认会保留 img_* 字面量，导致遍历出错
btrfs_path='/var/bocker' 所有子卷的存储根目录 必须是 Btrfs 文件系统
cgroups='cpu,cpuacct,memory' 启用的 cgroup 子系统 控制 CPU 和内存分配

选项解析机制

--BOCKER_CPU_SHARE=256 和 --debug 两种格式：

  • 带等号：declare "BOCKER_CPU_SHARE=256" → 生成变量 $BOCKER_CPU_SHARE=256
  • 不带等号：declare "BOCKER_debug=x" → 生成变量 $BOCKER_debug=x

设计意图：在命令行中临时调整资源限制，无需修改脚本。Docker 通过 --cpu-shares 和 --memory 参数实现类似功能。

3.2 辅助函数：bocker_check

原理分析

  • btrfs subvolume list 列出 /var/bocker 下所有子卷的 ID 和路径
  • grep -qw：-q 静默模式（只返回退出码），-w 精确匹配整个单词
  • 技巧：&& echo 0 || echo 1 将布尔结果转为字符串，方便在 [[ ]] 中比较

为什么不直接使用 test -d 判断目录？

因为 Btrfs 子卷虽然是目录，但普通目录检测无法区分”子卷”和”普通目录”。btrfs subvolume list 是权威的检测方式，确保操作的确实是 Btrfs 子卷。

3.3 镜像管理深入分析

3.3.1 bocker_init —— 从目录创建镜像

核心机制：Btrfs 写时复制（COW）

cp --reflink=auto 是关键。它利用了 Btrfs 的 Reflink（引用链接） 特性：

这意味着从目录创建镜像几乎是瞬时完成的，且不占用额外空间——直到修改文件时，才会逐块复制。

UUID 生成策略

shuf -i 42002-42254 -n 1 从 42002~42254（共 253 个值）中随机选一个。这是一个教学级简化：

  • 真实 Docker 使用 64 位十六进制 SHA256 hash（a1b2c3d4...）
  • Bocker 只有 253 个可用 ID，长时间运行必然碰撞
冲突处理的 bug

当 UUID 冲突时，本应递归调用 bocker_init 重新生成，但这里错误地调用了 bocker_run。由于 bocker_run 需要两个参数（image_id 和 command），而此处只传入了 $@（即目录名），会导致 bocker_run 执行失败。不过由于 253 个 ID 的碰撞概率极低，这个 bug 在实践中几乎不会被触发。

3.3.2 bocker_pull —— 从 Docker Hub 拉取镜像

镜像拉取流程
镜像层叠原理

Docker 镜像是分层叠加的：

Bocker 通过将所有层依次解压到同一目录（后一层覆盖前一层同名文件），实现了层的叠加合并。这与 Docker 的 UnionFS（OverlayFS）原理不同——Docker 保留各层独立，只在上层记录差异；而 Bocker 合并成单一文件系统。这意味着 Bocker 无法利用 Docker 的缓存复用（每一层可以独立缓存），但实现更简单。

3.3.3 bocker_images / bocker_rm

关键点：

  • img_* 前缀区分镜像，ps_* 前缀区分容器——命名约定取代了数据库
  • bocker_rm 同时删除 Btrfs 子卷和 cgroup。cgdelete 后的 || true 确保即使 cgroup 不存在也不报错
  • 对比 Docker：Docker 使用 etcd/数据库维护元数据，Bocker 用文件系统作为”数据库”

3.4 容器管理深入分析（核心）

3.4.1 bocker_run —— 容器创建与运行

这是 Bocker 最复杂的函数，也是理解容器运行时的关键。我将它拆解为 5 个阶段：

阶段1：网络设置详解

veth pair 的工作原理：

veth pair 像一个虚拟网线——两端永远连通，一端发送的数据另一端立即接收。将一端放入容器网络命名空间，另一端连接到主机网桥，就实现了容器与主机的网络互通。

IP 和 MAC 生成的简化策略：

  • UUID 为 ps_42150，取后三位 150 → IP 10.0.0.150，MAC 02:42:ac:11:00:1:50
  • 这种简化方式会导致 IP 冲突（若两位容器 ID 相同）和 IP 格式异常（如 10.0.0.0 被压缩为 10.0.0.）
阶段2：根文件系统 —— Btrfs 快照

这是 Bocker 最精妙的设计之一。Docker 使用多层 OverlayFS（lowerdir + upperdir + workdir），而 Bocker 使用单层 Btrfs 快照：

Btrfs 快照的写时复制（COW）特性：

  • 创建快照时不复制数据，只复制元数据
  • 当容器修改文件时，被修改的数据块才被复制到快照
  • 多个容器基于同一镜像运行时，共享未修改的数据块，极大节省磁盘空间
阶段3：cgroup 资源限制

cgroup 层级结构：

关键参数说明：

  • cpu.shares=512：相对权重，默认 1024，512 表示该容器获得默认一半的 CPU 时间
  • memory.limit_in_bytes=512MB：硬限制，超出则触发 OOM killer
  • : "${VAR:=default}" 是 Bash 的参数展开语法，当变量未设置或为空时使用默认值
阶段4：启动容器进程 —— 命令链解析

这是整个脚本最精妙的部分，一条命令链串联了 5 层隔离机制：

各层作用详解：

层级 命令 创建的命名空间 隔离内容
1 cgexec — CPU、内存资源限制
2 ip netns exec 网络命名空间 网络设备、IP、路由表
3 unshare -fmuip Mount、UTS、IPC、PID 挂载点、主机名、进程树
4 chroot — 根文件系统视图
5 mount -t proc — /proc 文件系统

unshare 参数详解：

参数 含义 Docker 对应
-f fork 子进程 必须，否则 --mount-proc 无效
-m 挂载命名空间 --mount
-u UTS 命名空间 --hostname
-i IPC 命名空间 --ipc
-p PID 命名空间 --pid
--mount-proc 自动挂载 /proc 需手动 mount -t proc

为什么需要 --mount-proc？

PID 命名空间隔离了进程视图。但 /proc 文件系统仍会显示宿主机的进程信息。--mount-proc 会在新 PID 命名空间中挂载一个只包含当前命名空间进程的 /proc，使容器内 ps aux 只能看到自己的进程。

阶段5：日志记录与清理

tee 同时输出到屏幕和文件，|| true 确保即使命令失败（返回非零退出码），脚本也不会因 set -e 而终止，从而执行后续的清理操作。

注意：网络清理只在容器命令执行完毕后进行。如果容器是后台长期运行的（如 Web 服务器），bocker_run 会阻塞直到容器退出。Bocker 缺少 Docker 的 -d（detach）模式。

PID 查找逻辑拆解

进程树关系：

3.4.3 bocker_commit —— 容器提交为镜像

流程：删除旧镜像 → 创建容器快照作为新镜像。注意：先 bocker_rm 删除旧镜像子卷，再创建新快照。如果 bocker_rm 失败（如旧镜像不存在），&& 会阻止后续操作。

3.5 帮助函数与入口

帮助文档的提取方式：从脚本自身提取以 #HELP 开头的注释，这种自文档化技术很巧妙。sed 替换 \n 为实际换行符来实现格式化输出。

命令分发模式：bocker_"$1" "${@:2}" 是典型的 Bash 命令分发模式，将 bocker run img_xxx cmd 映射为 bocker_run "img_xxx" "cmd"。

4. 核心技术原理深度探讨

4.1 Btrfs 子卷 vs Docker OverlayFS

特性 Bocker (Btrfs) Docker (OverlayFS)
存储后端 Btrfs 子卷 OverlayFS / overlay2
分层方式 每层合并为单一文件系统 保留独立层，差异覆盖
写时复制 Btrfs 快照 COW 文件级 COW（copy-up）
快照创建 瞬时 无需显式快照
空间效率 共享未修改数据块 共享未修改层
缓存复用 不支持（层已合并） 支持（每层独立缓存）
镜像推送 不支持 支持分层推送

Bocker 的简化：将多层合并为一层，牺牲了 Docker 的缓存复用能力，但代码复杂度大大降低。

4.2 命名空间隔离对照

Bocker 未实现的重要隔离：

  • 用户命名空间：容器内 root 即主机 root，安全隐患
  • cgroup 命名空间：容器内看不到宿主机的 cgroup 层级
  • SELinux/AppArmor：缺乏强制访问控制

5. Bocker 与 Docker 的对比

5.1 功能对比

功能 Bocker Docker
代码量 ~100 行 Bash 数百万行 Go
镜像拉取 Docker Hub V1 API Registry V2 API + 认证
镜像分层 合并为单层 多层 OverlayFS
容器隔离 Namespace + chroot Namespace + pivot_root
资源限制 cgroups (CPU/Memory) cgroups v2 + 更多子系统
网络 veth + bridge0 CNI/CNM 插件化

持久化 无 Volume 绑定挂载
构建 无 Dockerfile 构建

5.2 关键差异深度分析

1. 文件系统隔离：chroot vs pivot_root

chroot 只是改变当前进程的根目录，但不会切换全局根挂载点。这意味着理论上可以通过 chroot 逃逸（如 chroot 后的进程若拿到文件描述符，仍可访问宿主机文件系统）。pivot_root 则将整个系统根目录切换，安全性更高。

2. 容器进程管理

Bocker 的容器进程是 cgexec 的子进程，bocker_run 会阻塞等待。Docker 的容器进程是 containerd 的子进程，通过 runc 创建并分离，支持 docker run -d 后台运行。

3. 网络模型

Bocker 的 bridge0 是预创建的。Docker 的 docker0 网桥是自动创建和管理的，且支持用户自定义网络。

6. 设计缺陷与改进方向

6.1 已知缺陷

缺陷 位置 影响 改进方案
UUID 范围过小 bocker_init/bocker_run 最多 253 个容器 使用 mktemp -u 或 uuidgen
bocker_init 冲突处理 bug 第 5 行 极端情况无法正确重试 改为递归调用自身
IP 生成简化 bocker_run 可能冲突 使用 shuf 生成随机 IP
无后台运行模式 bocker_run 无法运行长期服务 添加 -d 参数，使用 & 后台
无用户命名空间 unshare 参数 安全风险 添加 --user 映射
网络清理不完整 bocker_run 末尾 容器崩溃时可能残留 添加 trap 清理

6.2 值得学习的设计亮点

尽管有缺陷，Bocker 的代码设计仍有不少亮点：

  1. 极致简约：100 行代码实现容器运行时，每行代码解决一个核心问题
  2. 自文档化：#HELP 注释自动生成帮助文档
  3. 命令分发模式：case 加动态函数调用，简洁优雅
  4. 利用 Linux 内核特性组合：不重复造轮子，直接调用 btrfs、ip、unshare 等工具
  5. Btrfs 快照作为容器层：巧妙利用 COW 特性，实现秒级容器创建

总结

Bocker 是一个精妙的容器技术教学项目。它用最少的代码让我们窥见了容器的本质：

每一行代码都对应一个内核特性，没有任何多余的抽象层。对于希望深入理解容器原理的开发者，Bocker 是一把绝佳的钥匙——它剥离了 Docker 的复杂性，直击本质。
