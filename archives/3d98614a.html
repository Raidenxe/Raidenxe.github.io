模拟面试题库与参考答案（运维开发 / 监控平台方向）

范围：Linux、Shell、Python、MySQL / Oracle / Redis / MongoDB、Java 运维与性能调优、Kafka、集中监控平台。
用法：先自己答一遍，再看答案；答案里的”链路”是面试官真正想听的骨架，命令和参数是血肉。

前言：这类岗位面试官到底在考什么

这个 JD 表面写着”较强 Shell 编写能力””掌握命令执行能力””能够独立进行数据库访问设计”，翻译成面试语言只有一句话：你过去是不是真的在线上干过活。

所以答案的黄金结构是三层：

  1. 结论先行——第一步看什么、做什么，一句话说清，不要绕。
  2. 链路完整——从现象到根因的分层排查路径要能一口气讲完（比如 CPU 100% 那套 top → PID → top -H → TID → jstack）。
  3. 能解释为什么——面试官追问的每一层都是在验证你是”背过”还是”做过”，命令背后的原理（为什么 du 和 df 对不上、为什么删了文件空间不释放）才是区分点。

面试官大概率不会按顺序问，而是挑一道深挖到底。下面 38 道题按你给的提纲整理，每道都带参考答案和追问解析。

一、Linux：不是问”大而全”，而是问你能不能干活

1. 线上 Linux 服务器 CPU 持续 90% 以上，登录后第一步看什么？

参考答案

第一步永远是 top，但只看三件事，别急着操作：

  • 上方 %Cpu(s) 一行的状态分布：us（用户态）、sy（内核态）、wa（IO 等待）、id（空闲）、hi/si（硬/软中断）。
  • load average 三个数，结合 CPU 核数判断负载是虚高还是真高。
  • 按 CPU 排序的进程列表，锁定是哪个进程在烧 CPU。

top 里重点看的字段：PID、%CPU、%MEM、COMMAND，以及上方 CPU 状态行。判断标准：单个进程 %CPU 长时间接近或超过 100%（多核时按核数叠加），基本就是问题进程。

追问解析

  • %us、%sy、%wa 分别代表什么？
    %us 是用户态 CPU，业务代码、JVM 里的应用线程跑在这里；%sy 是内核态 CPU，系统调用、中断处理、锁操作消耗在这里；%wa 是 CPU 等 IO 的时间占比，进程在等磁盘/网络。三者相加接近 100% 且 id 接近 0，说明 CPU 真的被吃满了；如果 wa 高但 us/sy 不高，说明瓶颈是磁盘而不是计算。

  • 如果发现 %sy 很高，你下一步怎么查？
    %sy 高说明内核在忙，常见原因有：系统调用过于频繁（比如某个循环反复做系统调用）、上下文切换太多、网络或磁盘中断打满单个 CPU。用 vmstat 1 看 cs（上下文切换）和 in（中断）列，用 pidstat -w 1 看哪个进程的 cswch 高，必要时 strace -p PID 跟一下系统调用。面试里能说出”先 vmstat 看上下文切换，再 pidstat -w 定位进程”就及格了。

  • 如果发现某个 Java 进程占了 80% CPU，你继续怎么查？
    先用 top -p PID 确认这个进程的 CPU 是持续性的，再用 pidstat -p PID 1 看是哪些线程在消耗。注意：JVM 的 GC 线程、JIT 编译线程（C2 CompilerThread）也会吃 CPU，先排除这两类，再看是不是业务线程。

    先看线程名：JVM 的线程名是有意义的（http-nio-8080-exec-N 是 Tomcat 工作线程、GC task thread 是 GC、C2 CompilerThread 是 JIT）。如果最耗 CPU 的是业务工作线程，抓 jstack 看它在跑什么；如果是 GC 线程，方向就转到堆和 GC 参数上，CPU 排查立刻变成内存排查。

2. 监控平台服务器磁盘空间 100%，但监控服务还能访问，你怎么处理？

参考答案

先确认再动手，顺序是：

  1. df -h 看是哪个挂载点满了、使用率多少。
  2. du -sh 逐层往下找大目录：du -sh /var/log/* | sort -rh | head，定位空间被谁吃掉。
  3. 判断哪些文件可以清理：日志、临时文件、旧备份、core dump，优先处理这类；业务数据文件先确认再动。

追问解析

  • df -h 和 du -sh 你分别看什么？
    df 看的是文件系统层面的使用情况（块设备的已用/可用），它反映的是”这个分区还能不能写”；du 是从目录树统计实际文件大小之和。df 管容量告警，du 管定位大文件。

  • df 显示 95%，但 du 加起来只有 60%，可能是什么问题？
    最常见的几个原因：一是已删除但仍被进程打开的文件（文件在磁盘上还被占用，但目录里已经看不到了，du 自然数不到）；二是保留块（ext4 默认预留 5% 给 root）；三是挂载点嵌套或有其他挂载点没被 du 覆盖；四是 du 权限不足统计不全（换 sudo）。面试能说出第一条”deleted 文件被进程持有”，说明真踩过这个坑。

  • 如何找到最大的日志文件？

    -xdev 防止进入其他挂载点（比如 /proc）。或者直接 du -sh /var/log/* | sort -rh | head -10。

  • 如果某个日志文件正在被 Java 进程持续写入，你会直接 rm 吗？
    不会直接 rm。直接 rm 有两个问题：进程持有的文件描述符还指向这个 inode，空间不会释放，而且日志照写不误，等于删了个寂寞。正确做法是先停写或轮转：用 logrotate 做轮转（copytruncate 选项能优雅地处理正在被写的文件），或者对文件做 truncate -s 0 先清零，再考虑后续删除。

  • 删除之后为什么磁盘空间可能还是不释放？
    因为空间是否释放取决于没有进程再持有这个文件，而不是目录里有没有这个文件名。rm 只是删掉了目录项，文件 inode 还在，直到最后一个打开它的进程关闭文件描述符。

  • 怎么定位哪个进程还持有这个文件？

    找到后要么重启进程（干净），要么确认业务无影响后处理。

  • 你会怎么设计日志轮转？
    生产环境用 logrotate 统一管：按大小（size 500M）或按时间（daily）触发，compress 压缩旧日志，rotate N 控制保留份数，关键的是对正在写的文件用 copytruncate（复制后清空原文件，写方句柄不受影响），对会重新打开文件的进程用 postrotate 发信号让它重开。应用侧能配合更好，比如 log4j2 的 RollingFileAppender 本身就是应用内轮转，和系统层 logrotate 二选一，别两个一起上把日志切乱。

3. 一个服务启动失败，让你先别看业务代码，只允许用 Linux 命令排查，你怎么查？

参考答案

先搭框架，再谈工具。排查顺序：

  1. 服务有没有被真正拉起来、以什么状态退出：systemctl status <svc> 看 Active 状态、Main PID、Exit code。
  2. 启动过程报了什么错：journalctl -u <svc> -n 200 --no-pager 看 systemd 视角的日志；再 tail -200 /var/log/<app>/app.log 看应用日志。
  3. 进程和端口状态：ps -ef | grep <app> 看进程是否存在、ss -lntp 看端口有没有监听。
  4. 依赖是否就绪：ss -lnt 确认 MySQL/Redis 端口、nc -zv <host> <port> 确认网络通不通、配置文件对不对。

追问解析（各命令的适用场景）

命令 什么时候用 看什么
ps 进程层面 进程在不在、父进程是谁、启动参数（-ef 带完整参数）
ss 网络连接/监听 端口有没有被监听、连接状态；替代老旧的 netstat
netstat 老系统/排查连接表 端口、连接数、TIME_WAIT 堆积
lsof 文件和端口归属 端口被谁占用、进程打开了哪些文件
grep 日志过滤 从日志里筛 ERROR/Exception/关键时间点
tail 日志跟踪 -f 实时看启动过程报错
systemctl 服务生命周期 服务状态、exit code、Restart 计数
journalctl systemd 日志 服务自身 stdout/stderr 之外的系统侧日志（OOM、依赖拉起失败）

面试官这么问，重点不是要你背命令，而是看你遇到问题的判断顺序：先系统侧（服务状态、exit code），再日志（journalctl、应用日志），再资源（进程、端口、依赖），最后一层才是业务代码。反过来先扒代码是运维的大忌。

4. 服务器能 ping 通，但是监控 Agent 还是连接不上，你怎么判断问题在哪里？

参考答案

ping 通只说明三层（网络层）通，后面每一层都可能断。按这条链路逐层验证：

  1. ping：三层通，确认主机在网。
  2. DNS：nslookup <agent-server> 或 getent hosts，确认 Agent 连接用的域名能解析、解析结果对不对。
  3. 路由：traceroute -n <server>，看中间哪一跳丢包或不通，确认四层以上的包能否到达。
  4. TCP 端口：nc -zv <server> <port>，确认目标端口 TCP 能连通。
  5. 防火墙：本机 iptables -L -n / firewall-cmd --list-all，云环境还要查安全组；常见坑是只放行了 ICMP（所以能 ping 通）但没放行 Agent 端口。
  6. 服务监听：在服务器上 ss -lntp，看 Agent 服务到底监听在 0.0.0.0 还是 127.0.0.1——监听在回环地址上，外部自然连不上，这是经典问题。
  7. Agent 配置：目标地址/端口写没写对、token/密钥是否一致、协议是否匹配（http/https/自定义 TCP）、Agent 进程本身是否存活。

能一口气把”ping 通 ≠ 能连上”讲清楚，并说出”检查监听地址是不是 127.0.0.1”这种真实坑，就证明你有大规模接入监控的实际经验（2100+ 台接入时，这类问题几乎每批都有）。

  • 怎么避免重复清理？
    用状态文件记录上次清理时间戳（上面的 STATE_FILE），两次清理间隔内不再触发；另一个思路是按文件 mtime 清理（只删 7 天前的），天然不会重复处理同一批文件。

  • 清理哪些文件？
    只碰白名单：日志轮转产生的旧文件（*.log.*）、超过保留期的临时文件、旧备份、core dump。业务数据、数据库文件、当前正在写的日志一律不碰。回答里强调”白名单 + 绝不 rm -rf 通配”是加分点。

  • 如果 /var/log 特别大怎么办？
    /var/log 大要分两步：先看是不是有进程把日志写飞了（du -sh /var/log/* 定位，lsof 看谁在写），光删文件不解决写飞的根因，几分钟又满了；然后上 logrotate 做轮转+压缩+保留份数，用 copytruncate 处理正在写的文件。如果日志里有敏感信息，还要考虑清空而不是删除（truncate -s 0 保留文件占位）。

追问解析

  • 并发怎么做？
    最轻量的是 xargs -P：cat server_ip.txt | xargs -P 10 -I {} ./check_one.sh {}；或者用 Shell 的 & + wait 手动控制；再进一步就是上 Python（paramiko + ThreadPoolExecutor），这也是面试官说”这道题很容易引到 Python”的原因——并发、超时、重试、结果收集，Python 都比 Shell 舒服。

  • 如果串行执行，大概有什么问题？
    慢是主要问题：200 台 × 每台 25 秒 ≈ 1017 分钟，加超时等待会更久；中途一台卡住可能把整批卡死；结果也没有聚合。

  • 如果 200 台机器同时执行，会不会把跳板机打爆？
    会。同时建立 200 个连接，跳板机/管理机的连接数、进程数、CPU 瞬间打满，SSH 服务端还有 MaxStartups 限制，超出后直接拒绝新连接，反而全挂。所以必须限并发。

  • 怎么限制并发数？
    xargs -P N 里的 N 就是并发上限，一般取 10~50 之间，根据管理机规格和网络调整；Python 里用 ThreadPoolExecutor(max_workers=20) 同理。并发不是越大越好，而是”让管理机保持忙碌但别被打爆”。

  • 超时怎么处理？
    SSH 连接层设 ConnectTimeout=5（连接建立超时）、ServerAliveInterval / ServerAliveCountMax（连接建立后的保活探测，防止挂死）；Python 侧 paramiko 的 connect(timeout=5)，再配合线程池的 future.result(timeout=...) 双保险。超时的机器记为失败，不阻塞整个批次。

  • 失败机器如何重试？
    失败 IP 写入文件，第二批只对失败列表重试，最多重试 N 轮（比如 2 轮），仍然失败的单独出报告给人处理。注意重试要限制轮数，避免无脑重试浪费时间。

追问解析

  • kill 完以后为什么不能直接认为重启成功？
    kill 只是发信号，它不保证进程退出，更不保证新进程能起来。进程可能没退干净（新进程起不来、端口占用）、可能启动过程中崩掉、可能起了但卡在初始化。一切以”可验证的状态”为准，不能以”命令执行成功”为准。

  • 怎么判断 JVM 真正起来？
    jps -l 能看到 JVM 进程（区别于 ps 只能看到 java 命令）；pgrep -f app.jar 也行。更严格的说法是：JVM 进程在 ≠ 应用启动完成，还要看端口和健康接口。

  • 怎么判断端口已经监听？
    ss -lnt | grep :8080，确认是 LISTEN 状态、监听地址对（0.0.0.0 还是 127.0.0.1 要看业务需要）。注意端口监听也分两种：容器/框架先监听了但业务还没初始化完。

  • 怎么判断应用已经 Ready？
    打健康检查接口：Spring Boot 用 /actuator/health（返回 {"status":"UP"}），自定义服务会有自己的 /health 或 /ready 接口。只看 "UP" 还不够，生产上健康检查要能反映数据库、Redis 等依赖——actuator/health 默认就带这些组件的探针。

  • 如果进程存在，但是接口还是不可用怎么办？
    不算重启成功，按启动失败处理：抓应用日志最后 100 行看卡在哪（连不上数据库、配置错误、Bean 初始化失败）；确认依赖（MySQL/Redis/Kafka）是否就绪；判断是不是启动脚本在等待什么（比如注册中心）。接口不可用就是失败，脚本要返回非零、进入失败处理，而不是放过去。这正是”平台上的命令执行能力”要体现的严谨性：判定标准可验证，失败有依据、有日志。

三、Python：不是考算法，而是考你能不能把运维工作程序化

8. 让你用 Python 做一个服务器巡检程序，你会怎么设计？

参考答案

不要讲语法，讲架构。我的设计是一条流水线，每一段职责单一：

具体到每一段：

  1. 配置读取：巡检项、阈值、并发数、超时统一放配置文件，代码里不写死；区分”全局配置”和”单机配置”。
  2. 服务器列表：从 CMDB 或独立文件读，字段至少包含 IP、业务、负责人、SSH 凭据引用；列表要和采集解耦，方便增删机器。
  3. 并发执行：ThreadPoolExecutor 每台服务器一个任务。
  4. 采集：SSH 上去执行命令（top/free/df/ss）或用 Agent 采集，解析成结构化结果；建议每台服务器一个独立函数，方便加巡检项。
  5. 结果汇总：收集所有机器的结果，写数据库或 CSV，能出”哪些机器异常、异常类型分布”的统计。
  6. 异常重试：连接失败/超时的机器重试 N 次，退避策略。
  7. 日志：每次巡检的进度、每台机器的结果、异常都落日志。
  8. 告警：异常结果按规则触发告警（对接钉钉/飞书/邮件/监控平台）。

追问：你为什么用多线程，而不是多进程？

因为巡检是典型的 IO 密集型任务：绝大部分时间花在 SSH 连接、等待远程命令返回上，CPU 几乎不参与。多线程模型下，一个线程在等网络 IO 时会释放 GIL，其他线程能并行推进，线程数=并发连接数，效率足够；多进程适合 CPU 密集型（比如大量计算），进程开销大、数量多了反而浪费。一句话：GIL 只卡计算，不卡 IO，所以 IO 密集任务线程池就够。另外 Python 侧还有一个理由：多线程共享内存，结果收集、失败列表维护比多进程传参简单得多。

9. 1000 台服务器同时巡检，你 Python 怎么实现？

参考答案

追问解析

  • 你选择 ThreadPoolExecutor 还是 asyncio？
    用 paramiko（同步阻塞）就是 ThreadPoolExecutor，简单直接，能复用成熟库；如果走 asyncio 必须换异步 SSH 库（如 asyncssh），网络 IO 层面吞吐更高，但代码复杂度和踩坑面都更大。面试里可以说：默认线程池，追求极致吞吐且团队能 hold 住异步时再上 asyncio。

  • 最大并发多少？
    100~200 之间比较合理。受三个约束：本机 fd 和线程资源、目标机器 SSH 服务端 MaxStartups 限制、网络带宽。1000 个并发不是不能起，而是没必要且容易把自己和目标打挂。

  • 为什么不是 1000 个线程？
    线程本身有创建/切换开销，1000 个线程光栈空间就吃 1~2GB 虚拟内存；线程切换频繁时 CPU 全耗在调度上；更重要的是 1000 个同时 SSH，目标机的 MaxStartups 会拒绝大部分连接，效果反而差。并发数量要匹配瓶颈资源，不是匹配任务数量。

  • 单台服务器超时怎么办？
    双层超时：paramiko 的 connect(timeout=) 管连接阶段；exec_command(timeout=) 或 channel.settimeout() 管命令执行阶段；线程池侧再兜一层 future.result(timeout=MAX)。超时后按失败处理，进入重试逻辑。

  • 某台机器 SSH 卡住怎么办？
    就是上面说的超时机制兜底——连接卡住由 connect 超时解决，命令执行卡住由命令超时解决，绝不会因为一台机器让整个巡检挂起。实践中 paramiko 偶尔有”超时了但线程还挂着”的情况，可以用带 timeout 的 as_completed + 放弃结果来兜，或者用进程级隔离（executor 的 shutdown 不等待挂死线程）。

  • 如何做重试？
    失败重试 2~3 次，用指数退避（0s、2s、4s…），区分错误类型：认证失败/主机不存在这类错误不重试（重试也白搭），连接超时/网络抖动才重试。

  • 怎么保证一个任务失败不会影响整个任务？
    每个任务内部 try/except 把异常吞掉转成失败结果返回，线程池提交后主线程只收集结果；这样任何一台机器挂了都只是 failed 列表里多一条，整体巡检照常完成。这是并发任务设计的基本功，面试官就是在等这句话。

11. 如果让你开发一个”监控平台命令执行模块”，Python 应该怎么设计？

参考答案

这个题对应 JD 里的”掌握相应平台上的命令执行能力”，核心不在 SSH 本身，而在安全、审计、超时、异步四个维度。

架构上分四层：

  1. 接口层：前端提交 {目标主机, 命令类型, 参数}，不是提交原始命令字符串。
  2. 校验层（安全）：
    • 命令走白名单：只允许预定义的命令类型（如 df、ping、jstack、restart），参数也校验/限制；
    • 参数化执行，避免拼接注入：用 shlex.split 解析参数，拒绝 ; && | ` $() 等 shell 元字符；
    • 危险命令黑名单兜底：rm -rf /、shutdown、mkfs、dd 等直接拒绝；
    • 权限控制：按”用户-角色-主机组”授权，只能对授权的机器执行授权的命令。
  3. 执行层：任务进入队列（数据库任务表 + 线程池/Celery 异步执行），并发限制、超时控制（命令超时强制 kill）、结果收集。
  4. 审计层：每次执行落库一条审计记录：执行人、执行时间、目标服务器、命令、参数、返回码、输出摘要、结果状态，可追溯、可查询。

追问解析

  • 前端传过来的命令怎么处理？ 结构化传参（命令类型+参数列表），后端按白名单模板拼装，而不是把整条命令字符串交给 Shell。这是防注入的第一道闸。
  • 如何防止命令注入？ 三层：参数白名单/校验、shlex.split 解析后逐项校验、绝不用 shell=True 拼接字符串（subprocess 默认 shell=False 且参数列表化）。
  • 怎么限制危险命令？ 白名单为主（没在白名单里的一律拒绝），黑名单兜底（高危命令即使参数变化也要拦）。白名单的粒度可以到”命令+参数模式”。
  • 怎么做权限控制？ 用户→角色→权限（命令类型、主机范围），执行前校验目标主机是否在授权范围内；敏感命令（重启、清理）单独加权限位。
  • 如何记录执行人、执行时间、目标服务器、命令、结果？ 审计表，字段：id, user, action_time, host, cmd_type, params, return_code, output, status, task_id；执行前写一条”待执行”，执行后回填结果，天然形成审计链。
  • 命令执行超时怎么办？ 执行线程设超时，超时后先 kill -TERM 再 kill -9 兜底，状态标记为超时失败；SSH 层用 paramiko timeout；数据库任务表里标记超时并允许重试或人工介入。
  • 批量执行失败怎么处理？ 单台失败不阻塞整体（第 9 题的思路），汇总失败清单；支持”只对失败主机重试”；失败原因（超时/认证/命令报错）分类展示。
  • 如何实现异步任务？ 任务表（状态机：PENDING→RUNNING→SUCCESS/FAILED/TIMEOUT）+ 后台线程池/Celery/RQ 消费；前端轮询或 WebSocket 拿任务状态。比同步接口强在：长任务不占请求线程、天然支持批量、可中断可重试。

扩展：权限模型——RBAC 五表设计（这道题的高分深挖点）

面试官大概率会追”权限具体怎么做”，别只答一句”用户-角色-主机组”。能把五张表讲出来，就是”真做过”和”背过”的分水岭。核心思想一句话：多对多关系不直接建外键，而是拆成两张关联表。

表 说明
t_user 用户（user_id 主键、username，可带 dept_id 做数据范围）
t_role 角色（admin / ops / viewer）
t_permission 权限点（菜单、接口；落到命令执行平台就是”可执行的命令类型”）
t_user_role 用户-角色关联，联合主键 (user_id, role_id)
t_role_permission 角色-权限关联，联合主键 (role_id, perm_id)

权限怎么算：user → user_role 拿角色集合 → role_permission 拿权限集合 → 去重取并集。SQL 就是两跳 join，这是 RBAC 的查询模型。

面试加分点：

  1. 为什么要关联表：多对多如果硬塞成逗号分隔的字段，查询要 LIKE、没法索引、没法约束；拆成关联表后联合主键保证唯一、可以加索引、查询走等值 join，还能在关联表上挂额外字段（如角色生效时间）。
  2. 权限粒度：RBAC 管”能不能干”，管不了”能干到什么范围”。落到命令执行平台，权限 = 命令类型 × 主机组 两个维度——一种做法是权限表带 host_group_id，另一种是独立的数据权限表（用户/角色 → 主机组）再和命令权限做交集判断。主动说出”权限只解决了能不能执行，数据范围要单独设计”，直接和只会背五张表的人拉开差距。
  3. 缓存：权限查出来之后缓存到 Redis（key 按用户），角色变更时清缓存；否则每次执行命令都查两跳 join，平台扛不住。这正好体现运维思维。
  4. 审计别放 RBAC 里：执行记录（谁、什么时候、对哪台机器、执行了什么）单独建审计表，别和权限表混——两个生命周期完全不一样。

12. 现在让你给一个 Java 应用设计 MySQL 数据库访问方案，你会怎么设计？

参考答案

方案的核心是连接池 + 参数化访问 + 监控三件套：

  1. 连接方式：JDBC（DriverManager.getConnection 或数据源方式），Java 侧用 MyBatis/JPA 封装，通过连接池（HikariCP / Druid）管理连接。
  2. 连接池配置：maximumPoolSize、minimumIdle、connectionTimeout、maxLifetime 按业务并发和数据库规格定，原则是”池大小 × 实例数 ≤ 数据库 max_connections 的 60%~70%，留余量”。
  3. 访问规范：所有 SQL 用参数化（PreparedStatement / MyBatis #{}），禁止拼接；读写分离按需做（读多写少时）。
  4. 监控：池的活跃/空闲连接数、获取连接等待时间、SQL 慢查询都要能观测（Druid 监控页或 Prometheus 指标），连接泄漏要靠池的检测机制兜底。

追问解析

  • JDBC 是怎么连接 MySQL 的？ 加载驱动（Class.forName("com.mysql.cj.jdbc.Driver")）→ DriverManager.getConnection(url, user, pass) 建立 Connection → 创建 Statement/PreparedStatement 执行 SQL → ResultSet 取结果 → 释放资源。连接的本质是 MySQL 协议握手（TCP + 认证 + 字符集协商），这也是它开销大的原因。
  • 为什么需要连接池？ 每次 getConnection 都要走完整的 TCP 握手 + 认证 + 协议协商，毫秒级开销，高频请求下光建连接就能把数据库打垮；连接池复用已建立的连接，把”建连”成本摊薄到几乎为零。
  • 常见连接池有哪些？ HikariCP（Spring Boot 默认，快、轻）、Druid（阿里，监控/慢 SQL 日志/防 SQL 注入内置能力强，国内 Java 团队常用）、DBCP/C3P0（老牌，新项目基本不用了）。
  • 最大连接数怎么设置？ 先看数据库侧 max_connections（默认 151），应用侧池大小按业务峰值并发估算，再留余量。经验值：单实例 maximumPoolSize 20~50 常见，但必须验算”连接池大小 × 应用实例数”是否撞到数据库上限；Hikari 官方建议池大小 ≈ (核数 × 2) + 有效磁盘数，实际上以压测为准。
  • 连接泄漏怎么发现？ 现象：池里的连接被借出不还，活跃连接数只涨不降，最终池耗尽。发现手段：Druid 的 leakDetectionThreshold（连接借出超过阈值记为泄漏并告警）、Hikari 的 leakDetectionThreshold；监控池的活跃连接曲线；代码上强制用 try-with-resources 保证归还。
  • 数据库连接池耗尽会出现什么现象？ 应用获取连接超时（Hikari 抛 SQLTransientConnectionException: HikariPool-1 - Connection is not available），请求线程集体阻塞在拿连接上，接口变慢直至大面积超时；数据库侧连接数打满，新连接被拒。

14. 让你设计数据库访问，你如何避免 SQL 注入？

参考答案

三层防线：

  1. 参数化（根本解法）：所有用户输入进 SQL 都走参数绑定——JDBC 用 PreparedStatement，MyBatis 用 #{}。SQL 结构和数据分离，输入永远只是”值”，不可能变成”可执行的语句片段”。
  2. 输入校验：业务侧对参数类型、长度、格式做白名单校验；特殊场景（动态表名、排序字段）用枚举白名单映射，杜绝直接拼接。
  3. 权限最小化：应用账号只授 SELECT/INSERT/UPDATE/DELETE，不给 DDL、不给 root；即使注入成功，能做的事也被锁死。

追问解析

  • PreparedStatement 原理？ 预编译：SQL 骨架先发给 MySQL 服务端解析、编译成执行计划并缓存，参数通过协议单独传输占位。所以参数再特殊也只是数据，不会参与 SQL 语法解析——这是它防注入的根本原因，顺带还有性能收益（执行计划复用）。
  • MyBatis 如何防 SQL 注入？ 用 #{} 时 MyBatis 生成 PreparedStatement 的占位符（?），参数走绑定，天然防注入。
  • $ 和 # 有什么区别？ #{} 是预编译占位符，安全；${} 是字符串直接拼接进 SQL（比如 ORDER BY ${sort}），不安全，且不能参数化。规范：${} 只允许用在白名单控制的表名/列名/排序字段上，且值必须经过白名单校验。
  • 数据库权限应该怎么设计？ 按角色最小授权：应用账号只给业务表的 DML，不给 GRANT/DDL；只读账号（报表、巡检）只给 SELECT；DBA 操作走独立的高权账号 + 审批。库、表级权限分开，生产/测试环境账号隔离。
  • 应用账号为什么不能直接使用 root？ root 权限无边界：能改表结构、能改权限、能删库，一旦应用侧被注入或代码 bug，破坏半径是整库而不是单表；root 也绕过了审计（无法区分是哪个应用在操作）。最小权限 + 可审计，是生产数据库的基本底线。

15. MySQL 一条 SQL 从 1 秒突然变成 20 秒，你怎么定位？

参考答案

按这条链路一路排，每一层有明确的验证动作：

  1. 确认慢 SQL 本身：慢查询日志（slow_query_log）或 performance_schema 里捞这条 SQL，拿到完整语句和耗时分布。
  2. EXPLAIN 看执行计划：重点看 type（ALL 全表扫描是信号）、key（走没走索引）、rows（预估扫描行数，和实际数据量对比）、Extra（Using filesort/Using temporary 都是性能杀手）。
  3. 索引：没走索引/索引失效（函数、隐式类型转换、前导通配符 %xxx）→ 补索引或改写法；走了索引但 rows 还是大 → 索引选择性差。
  4. 锁：SHOW ENGINE INNODB STATUS 或 information_schema.innodb_trx 看行锁等待、metadata lock（MDL 锁，DDL 和长事务互卡，线上经典问题）。
  5. 服务器资源：top/iostat/vmstat 看 CPU、磁盘 IO；数据没进内存时磁盘读放大（Buffer Pool 命中率低）。
  6. Buffer Pool：SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%' 看命中率，命中率低且库大 → innodb_buffer_pool_size 偏小。
  7. 连接池/应用侧：同一时刻连接池是否被占满、是否并发同一慢 SQL 互相放大；应用侧是否并发飙高。

回答时强调”先确认这是偶发还是持续、是这一条还是这一类 SQL”，然后从执行计划入手——EXPLAIN 之后 80% 的情况落在索引或锁上。

16. 你做过数据库备份，那你怎么证明”备份是有效的”？

参考答案

核心观点：备份没验证过就等于没有备份。证明有效分三层：

  1. 文件层：备份产物（如 .sql）要检查完整性——文件大小非零、结尾有正常结束标记（mysqldump 的 --dump-slave/注释结尾）、可解压可解析；mysqldump 加 --single-transaction --routines --triggers 保证一致性和完整性。
  2. 校验层：校验和比对（备份文件 sha256）、mysqlcheck 检查表结构完整性、备份日志里无报错。
  3. 恢复层（最重要）：定期在独立环境做恢复演练——把备份恢复到测试库，然后抽查数据一致性：总行数、关键表 checksum（CHECKSUM TABLE）、抽样数据对比，甚至跑一遍核心查询确认可服务。

追问解析

  • 单纯看到 .sql 文件存在能不能证明备份成功？ 不能。文件存在只能说明 mysqldump 命令跑完了（或没跑完但留下了半成品），不能说明数据完整、可恢复。常见翻车现场：磁盘满导致备份文件截断、脚本中途失败但文件在、备份的库根本不是线上那个。
  • 如何验证备份完整性？ 文件层：大小、行数、结尾标记、校验和；结构层：mysqlcheck / 导入到临时库看报错；数据层：恢复后 CHECKSUM TABLE 和源库比对（或与上次备份比对）。
  • 如何做恢复测试？ 定期（比如每月）把最新备份恢复到测试实例，执行：表数量/行数核对、checksum 比对、代表性查询、应用冒烟。恢复测试要纳入备份制度，不能想起来才做。
  • 全量 + 增量怎么设计？ 全量备份（每周/每天，mysqldump 或物理备份 XtraBackup）+ 增量基于 binlog 重放（记录备份时刻的 binlog 文件+位点，之后把该位点之后的 binlog 按时间片归档）。恢复时：全量恢复 → 追增量 binlog 到目标时间点。
  • binlog 怎么配合？ 备份时记录 SHOW MASTER STATUS 的 File + Position（或 GTID），这就是增量起点；binlog 要开启并设置 expire_logs_days/binlog_expire_logs_seconds 让保留期覆盖备份周期，确保增量链不中断。
  • 数据库迁移以后怎么接着同步源库产生的数据？ 迁移完成 ≠ 数据同步完成：源库在迁移期间还在写。做法：迁移前记录 binlog 位点，迁移完成后继续消费/重放源库该位点之后的 binlog（用 Canal / DataX / 自研 binlog 消费脚本），把增量追平后再做一致性校验，最后才切换写流量。这个回答对应简历上的真实迁移经历，能讲出”位点 + 增量追平 + 切换”三步就是实战过的。

17. 你实际用得最多的是 MySQL，Oracle 你主要做过什么？

参考答案

如实交代接触深度（比如：做过 Oracle 上的查询分析、慢 SQL 定位、表空间监控、数据迁移，没有像 MySQL 那样完整负责过），然后立刻把对比讲出来，展示你知道差异在哪：

维度 Oracle MySQL
架构 实例（SGA/PGA）+ 数据库，共享内存管理 单进程多线程架构（8.0），存储引擎层
存储 逻辑结构：表空间 → 段 → 区 → 块，数据文件组成表空间 表空间/独立表空间，由 InnoDB 管理
分页 ROWNUM/FETCH FIRST，无 LIMIT LIMIT n,m
空值 空字符串视为 NULL 空字符串和 NULL 不同
事务/锁 默认读不阻塞写（MVCC+回滚段），行锁 InnoDB MVCC，行锁（有锁间隙/死锁检测）
高可用 RAC（共享存储集群）、DataGuard（物理/逻辑备库） 主从复制、MGR、半同步
运维 表空间满、undo 表空间、AWR 报告 慢日志、processlist、Buffer Pool

追问解析

  • Oracle 和 MySQL 最大区别？ 一句话版：Oracle 是”实例 + 数据库”的大而全体系，强调企业级功能（RAC、DataGuard、AWR、细粒度权限），SQL 和存储逻辑都是自己的体系；MySQL 是”轻量 + 存储引擎插件化”（InnoDB/MyISAM），靠主从复制和中间件横向扩展。运维上最大的体感差异：Oracle 的表空间管理、undo/temp 空间是日常重点，MySQL 的重点是慢 SQL 和主从。
  • Oracle 怎么查看当前连接？ SELECT sid, serial#, username, machine, program, status FROM v$session;，v$session 就是 Oracle 版的 processlist。
  • 怎么定位慢 SQL？ 三个入口：v$session 里找 SQL_ID → 用 SQL_ID 查 v$sql/v$sqlarea 拿 SQL 文本和执行统计；或直接出 AWR 报告（awrrpt.sql）看 Top SQL；再看执行计划（DBMS_XPLAN.DISPLAY_CURSOR）。Oracle 的慢 SQL 定位比 MySQL 更体系化，AWR 是 DBA 的标配工具。
  • 表空间是什么？ Oracle 的逻辑存储容器：数据按 表空间→段→区→块 组织，表空间由一个或多个数据文件（.dbf）组成，表/索引创建时落在某个表空间里。类比 MySQL：表空间 ≈ 一个”容器”，对应磁盘上的数据文件。
  • Oracle 为什么会出现表空间不足？ 最常见：数据文件达到 maxsize 或自动扩展（AUTOEXTEND）没开/被关；undo 表空间被长事务撑爆（经典，大事务回滚段暴涨）；temp 表空间被大排序/大哈希撑爆；还有表空间碎片。运维日常就是监控表空间使用率 + 提前加数据文件或开自动扩展。

18. Redis 在你的项目里承担什么角色？为什么不用 MySQL？

参考答案

我的项目里 Redis 承担四类角色：缓存（热点数据，扛读流量）、计数器/限流（QPS 统计、接口限流、库存扣减的原子操作）、分布式锁（多实例互斥，如批量任务的排他执行）、轻量队列（发布订阅、延迟队列）。选 Redis 而不是 MySQL 做这些事，核心就一句话：MySQL 是把数据”落盘管起来”，Redis 是把数据”放在内存里快取快读”，两者是不同成本结构的工具——缓存/计数场景要求的是纳秒级读写和原子操作，MySQL 的磁盘 IO 和行锁在这个场景下成本高一个数量级，且扛不住同样的读写并发。

追问解析

  • Redis 数据类型？ string（缓存、计数器）、hash（对象/字段级存取）、list（消息队列、最新列表）、set（去重、共同好友）、zset（排行榜、延迟队列，按分数排序）、另外还有 stream（真正带 ack 的消息队列）、bitmap、HyperLogLog。
  • 缓存穿透？ 查一个不存在的数据，缓存永远没有，请求全部打到数据库。解决：① 空值也缓存（设短过期）；② 布隆过滤器在缓存前拦截不存在的 key；③ 参数校验兜底。
  • 缓存击穿？ 一个热点 key 过期的瞬间，大量请求同时打到数据库。解决：① 互斥锁（只让一个请求回源，其他等待）；② 逻辑过期（value 里带过期时间，异步刷新）；③ 热点 key 不过期 + 后台续期。
  • 缓存雪崩？ 大量 key 同时过期（或 Redis 整体宕机），请求洪峰全压到数据库。解决：① 过期时间加随机值错峰；② 多级缓存（本地缓存 Caffeine + Redis）；③ Redis 高可用（哨兵/集群）避免整机宕机；④ 限流降级兜底。
  • Redis 持久化？ RDB（定期快照，恢复快、可能丢最后一次快照后的数据）和 AOF（追加写，丢数据少、文件大、恢复慢），4.0 后有混合持久化（RDB 基座 + AOF 增量）。选型：允许丢分钟级数据用 RDB，要尽量不丢用 AOF，默认混合。
  • Redis 内存满了怎么办？ 靠 maxmemory + 淘汰策略：noeviction（不淘汰，写报错）、allkeys-lru/volatile-lru（按 LRU 淘汰）、allkeys-lfu/volatile-lfu（按 LFU）、volatile-ttl（优先淘汰快过期的）。选型逻辑：缓存场景用 allkeys-lfu 或 allkeys-lru；有持久化要求的键要小心淘汰。更根本的解法是扩容/加节点，淘汰只是兜底。

19. MongoDB 和 MySQL，你什么时候会选 MongoDB？

参考答案

选型看四点：数据模型、事务需求、写入规模、查询方式。

选 MongoDB 的场景：① 数据是文档/JSON 形态（配置、日志、埋点、IoT 数据），字段不固定，用文档模型比关系表舒服；② 高写入量、水平扩展优先（Mongo 分片是原生的）；③ 查询就是按 key/范围查，不需要复杂 join；④ 对强事务要求不高（MongoDB 4.0+ 支持事务，但能力与生态仍弱于 MySQL）。

选 MySQL 的场景：① 强事务、强一致（订单、支付、账务）；② 复杂关联查询、报表统计；③ 团队熟悉度、生态工具（binlog 同步、ORM、运维体系）。

一句话总结：关系型数据、钱相关、要 join 要事务的选 MySQL；海量、写多、结构松散的选 MongoDB。面试官听的是你有没有选型判断力，而不是背书。

20. 你自己不一定是 Java 开发，现在让你接手一个 Spring Boot 服务，你怎么判断它是否运行正常？

参考答案

按”由外到内、由表到里”的清单过一遍，每一层都有具体命令：

  1. 进程：ps -ef | grep java / jps -l，确认 JVM 进程存活、启动参数正确。
  2. 端口：ss -lntp | grep <port>，确认监听正常。
  3. 日志：tail -f /var/log/app/app.log，最近时段有没有 ERROR、异常堆栈、频繁重试。
  4. JVM：jstat -gcutil <pid> 1000 看内存和 GC 曲线，jmap -heap <pid> 看堆配置；jstack <pid> 看线程。
  5. 接口：curl http://127.0.0.1:<port>/actuator/health 看整体状态，再探关键业务接口的耗时和返回码；/actuator/metrics 看 HTTP 请求量、线程池指标。
  6. 线程：jstack 里有没有大量 BLOCKED/WAITING 堆积，Tomcat 工作线程（http-nio-xxx-exec-N）数量是否健康。
  7. GC：jstat -gcutil 看 YGC/FGC 频率、GC 耗时；Full GC 频繁是内存问题信号。
  8. 数据库连接：看连接池指标（Druid/Hikari 的活跃连接数），以及数据库侧该应用来源的连接是否正常。

最后综合判断：进程在、端口在、健康接口 UP、日志干净、GC 平稳、连接池有余量——这才叫”运行正常”。面试官想听的是：你不是只会看进程，而是有完整的健康检查维度。

21. Spring Boot 服务启动失败，你会从哪些方面排查？

参考答案

通用思路先讲：看完整日志而不是只看报错标题——Spring Boot 启动失败，异常堆栈的 Caused by 链才是根因，多数时候顺着最底下的 cause 就能定位。然后按错误类型分诊：

  • Failed to configure a DataSource：pom 里带了 spring-boot-starter-jdbc / 数据源相关依赖，但配置里没有数据源或连接不上。先查 application.yml 的 spring.datasource.* 是否完整、数据库是否可达。
  • BeanCreationException：Bean 创建失败，常见是依赖注入不满足（缺配置、Bean 不存在、循环依赖）。看堆栈里创建的是哪个 Bean、缺哪个依赖。
  • OutOfMemoryError：JVM 内存不足，查启动参数 -Xmx 是否合理、堆是否瞬间被撑爆；配合 dump 分析（见题 25）。
  • Connection refused：依赖服务（MySQL/Redis/Kafka/注册中心）没起来或地址端口配错，nc -zv 验证网络。
  • Port already in use：端口被占，ss -lntp / lsof -i:<port> 找到占用进程，是旧实例没退干净还是别的服务。

排查顺序总结：日志（完整堆栈）→ 配置（数据源/依赖地址）→ 依赖服务（网络连通）→ 资源（端口/内存）。最后才是业务代码。

22. 你怎么判断一个 Java 服务到底是应用问题、JVM 问题还是数据库问题？

参考答案

这是一个分层判断题，思路是用指标排除法 + 耗时分布定位：

  1. 先看影响面：是所有接口都慢，还是个别接口慢？全慢 → 大概率是共享资源（JVM/数据库/线程池/网络）；个别慢 → 大概率是应用代码或特定依赖。
  2. 看数据库侧：数据库 CPU、Threads_running、慢 SQL 数、锁等待是否异常。数据库忙 → 问题在 DB（慢 SQL、锁、容量），此时接口慢只是症状。
  3. 看 JVM 侧：jstat -gcutil 看 GC 频率和耗时。Full GC 频繁 → JVM 内存/GC 问题；GC 正常但接口慢 → 排除 JVM。
  4. 看线程侧：jstack 看线程状态。大量 BLOCKED 等锁 → 锁竞争；工作线程耗尽 → 线程池问题；大量线程在 JDBC 调用上 → 问题在下游数据库。
  5. 看应用侧：接口耗时的内部构成（Arthas trace 能按方法拆耗时），定位慢在哪一段代码/哪个调用。

判断口诀：先看有没有慢 SQL 和数据库异常（数据库问题最常见），再看 GC 和堆（JVM 问题），最后才是应用代码。面试官要的就是这个”先排除后定位”的思维，而不是上来就猜。

23. 线上 Java 应用 CPU 100%，完整排查流程是什么？

参考答案

这是必考题，完整链路：

定位到线程栈之后看三件事：

  1. 线程名：GC task thread → 是 GC 在烧 CPU，方向转向堆内存；C2 CompilerThread → JIT 编译热（通常正常，看是否持续）；http-nio-xxx-exec-N → 业务工作线程，看它跑在哪。
  2. 栈帧：RUNNABLE 状态 + 栈顶出现业务包名（com.xxx.xxx）的方法 → 就是业务代码死循环/高频计算；栈顶是 JDK 类库（java.util.HashMap、正则、加密）→ 定位到具体调用方。
  3. 多次抓栈对比：线程一直卡在同一段代码 → 死循环或锁旋转；每次栈不一样 → 可能是高吞吐计算。

生产上补一句加分话：jstack 抓之前先 jstat -gcutil 排除 GC 因素，抓栈时多抓 3 次间隔 3 秒，避免抓到一个瞬时状态误判。

24. Java 服务频繁 Full GC，你怎么排查？

参考答案

排查链路：

  1. 先确认事实：jstat -gcutil <pid> 1000 连续观察，看 FGC 次数和间隔、O（老年代）占比。Full GC 多久一次、每次 STW 多久，先量化。
  2. 看对象去向：S0/S1/E 看新生代，O 看老年代。老年代使用率持续高位不降 → 有对象堆积。
  3. 找堆积原因，按可能性排：
    • 新生代太小：YGC 频繁、对象没来得及回收就晋升老年代；
    • 大对象：超大数组/集合直接进老年代（-XX:PretenureSizeThreshold 相关）；
    • 内存泄漏：老年代只涨不降（静态集合、缓存不清理、类加载器泄漏）——这是最严重的情况；
    • GC 参数不合理：堆太小（-Xmx 不够）、或用了不适合的 GC（吞吐优先 vs 延迟优先）。
  4. 取证：jmap -dump:format=b,file=/tmp/heap.hprof <pid> 抓 Heap Dump（生产注意暂停影响），用 MAT 分析（看支配树找大对象、Leak Suspects 报告）。
  5. 处置：参数调优（堆大小、GC 器选择、-XX:NewRatio）解决配置问题；代码修复解决泄漏问题；临时手段是扩容/摘流量。

关键判断：Full GC 后老年代能不能降下来——能降是”量的问题”（参数/容量），不能降是”质的问题”（泄漏），这是面试官最想听到的分水岭。

25. Java 应用内存一直涨，但是没有 OOM，你怎么判断是不是内存泄漏？

参考答案

判断泄漏的本质：内存只涨不降，且 GC 后回不来。

排查步骤：

  1. 观察曲线：jstat -gcutil <pid> 定期采样，画堆内存/老年代使用率曲线。正常是有波动的（涨-回收-涨），泄漏是持续单调上升、每次 Full GC 后只降一点点又涨回去。
  2. 拿 Heap Dump： 注意：大堆 dump 会卡住 JVM（STW），生产要挑低峰期或先用 jmap -histo 看一眼对象分布。
  3. MAT 分析：导入 dump 后看三样——Histogram（各类型对象数量和大小，哪个类的实例数异常大）、Dominator Tree（支配树，按”保留内存”排大对象）、Leak Suspects（MAT 自动怀疑泄漏的路径）。重点看”哪类对象一直增长”：如果是业务对象（com.xxx），看它的引用链（Path to GC Roots），谁持有它不放；如果是 byte[]/集合，看被谁引用。
  4. 定位代码：从 MAT 的引用链往回推，找到”本该释放却被长期持有”的点。常见泄漏源头：静态集合只增不减、缓存没有过期策略、未关闭的资源（流/连接）、ThreadLocal 未清理、类加载器泄漏。

回答里体现”histo 看分布 → dump 看引用链 → 代码定位“三步，就是完整闭环。

26. Java 应用接口突然从 100ms 变成 5s，但 CPU 和内存都正常，你查什么？

参考答案

CPU 和内存正常，说明不是计算和堆的问题，方向转向等待。按”等什么”排查：

  1. 线程池：jstack 看工作线程状态。如果线程都 Blocked/Waiting 或线程数打满、任务在队列堆积 → 线程池耗尽，看是谁占了线程。
  2. 数据库：接口是不是在等 SQL？查慢 SQL、锁等待（processlist、innodb_trx），数据库连接池获取是否超时。
  3. 连接池：应用自身连接池（Redis/MySQL）是否耗尽，获取连接在排队。
  4. 锁：jstack 里大量线程 BLOCKED 且 waiting to lock 同一个对象 → 锁竞争或死锁。
  5. GC：jstat -gcutil 确认——GC 次数不多但单次 STW 长（比如老年代 GC 器配置不当），同样会拖慢接口。
  6. 下游服务：接口调用了别的服务/API，下游慢了接口就慢。用 Arthas trace 或日志看耗时在哪一段（是自己代码、DB、Redis 还是 HTTP 调用）。
  7. 磁盘 IO：日志写盘、数据文件落盘是否成瓶颈，iostat -x 1 看 %util 和 await。
  8. 网络：TCP 重传、带宽打满（sar -n DEV），跨机房调用尤其要查。

28. 为什么一个 Consumer 消费不过来？

参考答案

从吞吐公式拆：消费速率 = 分区数 × 单分区消费速率，所以消费不过来无非四个原因：

  1. Consumer 数量不够或超过分区数：一个分区同一时刻只能被组内一个 consumer 消费，consumer 数超过分区数的部分完全空闲；consumer 数小于分区数则必然有分区消费慢。
  2. 单条消息处理耗时过长：消费逻辑里有慢操作（同步调下游 API、写库慢、复杂计算），处理时间是吞吐的第一瓶颈。
  3. 频繁 Rebalance：consumer 心跳超时、处理耗时超过 max.poll.interval.ms、加入/离开组，都会触发 rebalance，rebalance 期间整个组停止消费，lag 只涨不消。
  4. 下游瓶颈：消费要写数据库/调下游接口，下游慢了消费就慢；DB 连接池打满、下游 API 超时，都会拖住 consumer。

追问解析

  • Consumer 数量和 Partition 数量什么关系？ 一个分区同一时刻只分配给组内一个 consumer；consumer 数 ≤ 分区数时，增加 consumer 能线性提升吞吐；consumer 数 > 分区数时，多出的 consumer 空转。所以提升消费能力要么加分区（改 topic 分区数），要么在 consumer 数不大于分区数的前提下加 consumer。
  • 单条消息处理耗时怎么定位？ 看 consumer 日志里每条消息的处理耗时（或打点监控），用 Arthas/profile 看消费方法内部慢在哪：是反序列化、写库、调下游还是锁等待。顺手看消息大小——消息体太大也会拖慢。
  • Consumer 是否频繁 Rebalance？ 看消费组的 kafka-consumer-groups --describe 里成员变化，或监控 rebalance 次数（kafka.consumer:type=consumer-coordinator-metrics 的 rebalance-rate）。原因通常是：心跳超时（网络抖动、GC 停顿）、处理太慢超过 max.poll.interval.ms、session.timeout.ms 设置太小。
  • 数据库是不是瓶颈？ 消费端批量写库时，看 DB 的活跃连接、慢 SQL、锁等待；把”写库”从消费主链路里拆出来（批量攒批、异步写），吞吐立刻改善。
  • 下游 API 是否慢？ 如果消费里同步调下游，下游 P99 变高会直接吃掉消费速率；对策是超时/熔断/降级，或改成异步投递。

29. Kafka 消息为什么会重复消费？怎么解决？

参考答案

重复消费的机制链：

根因就是一条：offset 的提交时机晚于业务处理完成，且提交与业务处理不是原子的。所以重复消费在 Kafka 语义下无法绝对避免（除非用事务做到恰好一次），工程上的标准解法是消费端幂等。

解决思路分三层：

  1. 幂等消费（根本解法）：业务处理做成幂等——用业务唯一键（订单号、消息 ID）去重：消费前查去重表/Redis set，已处理过直接跳过；或数据库用唯一索引 + INSERT ... ON DUPLICATE KEY 兜底。这是任何消息系统的通用解法。
  2. 调整提交策略：处理完再提交（enable.auto.commit=false + 手动提交），把重复窗口缩小到”处理完但没提交”这段；但注意手动提交提前会丢消息（处理中崩溃），提交延后则重复更多——这是个 trade-off，丢 vs 重，通常重比丢好。
  3. 恰好一次（高要求场景）：Kafka 事务（producer 事务 + read_committed consumer）或”消费-处理-提交”放进同一个事务，成本高、有性能代价，多数场景用不上。

追问解析

  • Offset、Commit 是什么？ offset 是分区内消息的序号（消费位置），consumer 处理完后把新位置提交给 broker，组内其他人（或自己重启后）从提交的位置接着消费。commit 就是”声明我消费到哪了”。
  • Consumer 崩溃和重平衡怎么导致重复？ 崩溃或 rebalance 的瞬间，未提交的 offset 会”回滚”到最后一次提交点，这一段消息被重新拉取。rebalance 越频繁，重复窗口被打开得越多。
  • 为什么幂等是最终解法？ 因为无论怎么调提交策略，都做不到”恰好消费一次”（at-most-once 会丢、at-least-once 会重），只有业务层幂等让”重复”无害。面试官追到这里就是看你说不说得出”幂等兜底”。

30. Kafka Producer 发送失败，你怎么判断是应用问题还是 Kafka 问题？

参考答案

先看报错在”哪一段”：producer 发送链路是 应用 → 网络 → broker（Topic/分区 Leader）→ 落盘（ISR）。逐层验证：

  1. Broker 是否存活：kafka-topics.sh --bootstrap-server <broker> --list 或监控 broker 进程；连接失败先 nc -zv 验证 TCP。
  2. TCP 是否正常：到 bootstrap broker 的 9092 端口连通性、网络抖动、防火墙。
  3. Topic 是否存在：producer 配错 topic / 未开启 auto.create，kafka-topics.sh --describe 确认。
  4. Partition Leader 是否正常：--describe 里看分区 leader 和副本，Leader: -1 表示无 leader（broker 挂了未恢复）。
  5. ISR 是否同步：ISR 列表比副本数小 → 副本落后或离线，min.insync.replicas 不满足时会直接报 NotEnoughReplicas。
  6. 磁盘：broker 磁盘满，消息写不进去，报 DiskError/LogDir 相关错误。
  7. acks 设置：acks=all 要求 ISR 全部确认，对 broker/网络更敏感；acks=0/1 容忍更多但可能丢。
  8. 超时参数：request.timeout.ms、delivery.timeout.ms、retries、max.block.ms——重试耗尽、缓冲区满（buffer.memory）、元数据请求超时都会让 send 回调报错。

判断结论的框架：报错在”连接/元数据”阶段多半是网络或 broker；报错在”写日志/ISR 确认”阶段多半是 broker 侧（磁盘、副本、配置）；同一时刻其他 topic 正常而只有这个 topic 失败，多半是 topic 或 key 路由问题。

33. 如果监控系统突然产生大量告警，你怎么判断是真故障还是监控本身故障？

参考答案

关键判据是告警的面：是”全局告警”还是”局部告警”。

  1. 看影响面：如果同时段、多台不相关机器、多个不同指标一起告警 → 大概率是监控系统自身问题（监控 Server 挂了、采集链路故障、网络分区）；如果只是某几台相关机器/某类指标告警 → 更可能是真实故障。
  2. 验证监控链路各层：
    • Agent/Exporter 是否正常：进程在不在、有没有批量失联（批量失联 = 采集链路问题）。
    • Server 是否正常：监控 Server/Proxy 的 CPU、负载、队列积压。
    • 网络是否正常：Agent 到 Server 的网络、丢包；跨网段批量告警时优先怀疑网络。
    • 指标是否停止更新：看 Grafana 里数据有没有断点/空洞；指标新鲜度（时间戳是否停在某个时间）是监控故障的强信号。
    • 时间戳有没有异常：如果告警时间戳集中在某一秒，可能是一次性的采集/评估积压；时钟漂移也会造成假告警。
  3. 判断告警风暴特征：同一规则同时触发几百条（如”主机磁盘>80%”全量触发，而磁盘其实没满）→ 规则配置错误（阈值单位错、正则错、边界判断错）。
  4. 误报排查：看原始数据 vs 告警阈值——数据本身没超，告警却出来了，那就是规则/采集的问题；数据确实超了，才是真故障。

处理原则：先救监控（确认监控本身可信），再谈故障处理——监控不可信时，所有判断都是猜。

34. 如果 JVM 应用已经不可用，但是监控平台没有告警，你认为是哪一层出了问题？怎么定位？

参考答案

把完整链路画出来，然后逐层排查”断在哪”：

逐层定位：

  1. 业务/JVM 层：确认应用真的不可用（进程、端口、接口）；假死（线程池耗尽、GC 长时间停顿）时进程在但服务不可用，监控必须靠”业务探针”才能发现——主机监控天然发现不了。
  2. 采集层：Exporter/Agent 是否存活、指标是否还在上报（看监控里该主机的指标新鲜度）；JVM exporter 挂了 = 数据停更 = 没告警。
  3. Server/数据层：Prometheus/Server 是否收到该 target 的数据、target 是否处于 Down 状态（如果采集本身有”up”指标，这个会先告警）。
  4. 规则层：告警规则阈值是否合理、表达式是否写错（比如 process_uptime < 1 写成 >）、规则是否被静默（silence）或静默未解除。

37. 现在监控平台发现一个 Java 服务频繁重启，你怎么处理？

参考答案

不要直接说”看日志”，按这条链路排：

关键排查动作：

  1. **确认”谁在重启它”**：systemctl status 看 Restart 计数和退出码；journalctl -u <svc> -n 200 看 systemd 视角的重启原因。退出码 137 通常是 kill -9（可能是 OOM killer 或外部强杀），143 是 kill -15。
  2. 查 OOM：dmesg | grep -i oom / journalctl -k 看内核 OOM killer 是否杀了 JVM（进程被 OOM kill 时应用日志里反而没有 Java 堆栈，这是关键区分点）；JVM 自身 OOM 则在应用日志里有 OutOfMemoryError 堆栈。
  3. 看崩溃时间点上下文：每次崩溃前后应用日志、数据库、Kafka、下游是否同步异常——如果是依赖挂导致启动失败-重启-再失败的循环，修依赖才能止血。
  4. 看启动是否真的成功过：频繁重启往往是”起不来”（启动失败被 systemd 拉起再失败），而不是”起来后被打死”——两个方向完全不同，先用日志区分。

回答要点：**先分清”起不来”还是”起来后被杀死”**（systemd/exit code/OOM 三条证据），再顺着崩溃点看依赖。这是监控平台值班最常见的场景之一。

  3. 补文档：把架构图、服务清单、依赖关系、应急联系人整理成接手文档，别信口口相传。

“陌生平台接手”考的不是技术深度，是系统性：你有没有一套固定的接手方法论。上面十维度 + “先跑健康巡检、先验证告警链路”就是方法论。

十一、按这个 JD 真正需要重点准备的 15 道题

不是把 38 道全背熟，而是把下面这些练到面试官连续追问 5 层也不崩。速查表：

# 题目 核心链路 / 一句话答案 追问点
1 CPU 100% 定位 Java 线程 top → top -H → TID → printf %x → jstack → 栈顶业务包名 GC 线程 vs 业务线程怎么区分
2 Java 频繁 Full GC jstat -gcutil → 老年代是否只涨不降 → 参数 or 泄漏 Full GC 后能不能降下来
3 接口突然变慢但 CPU 正常 jstack 看等什么 → 线程池/锁/DB/连接池/GC/下游/IO 全慢 vs 个别慢
4 Python 巡检 1000 台 线程池限并发 100~200 + 超时 + 重试 + 失败隔离 为什么不是 1000 线程
5 Shell 批量执行命令 xargs -P 限并发 + ConnectTimeout + 失败重试 会不会打爆跳板机
6 设计命令执行平台 白名单 + 参数化 + 权限 + 审计 + 异步任务表 如何防命令注入
7 MySQL 连接数打满 processlist 分 Query/Sleep → 慢 SQL / 锁 / 池配置 Threads_connected vs Threads_running
8 SQL 突然变慢 EXPLAIN → 索引 → 锁 → Buffer Pool → 连接池 偶发 vs 持续
9 数据库迁移后持续同步 记录 binlog 位点 → 增量追平 → 校验 → 切换 增量怎么证明追平
10 Kafka 消息积压 先看 Consumer Lag → Consumer 死/慢 → 分区 → broker → 下游 消费不过来拆吞吐公式
11 Kafka 重复消费 未提交 offset + 崩溃/rebalance → 重复；幂等兜底 提交时机 trade-off
12 Spring Boot 启动失败 完整堆栈 Caused by → 配置/依赖/端口/内存分诊 DataSource 报错怎么看
13 2100+ 服务器接入监控 CMDB → 批量安装 → Proxy 分层 → 自动验证 → 告警分级 怎么验证接入成功
14 JVM 监控指标怎么采 jstat/Actuator/exporter → heap/GC/线程/类，对应 Prometheus 指标 假死为什么采不到
15 设计集中监控系统 采集（Agent/Exporter）→ 存储（TSDB）→ 规则 → 告警 → 通知 → 自监控 监控自身的告警

结尾：怎么用这份材料练

38 道题的价值排序是：第 23（CPU 定位）、24（Full GC）、35（接口超时全链路）、36（巡检平台设计）、31（大规模接入监控）、33（告警风暴判断） 这几道最贴近 JD 和简历交叉点，优先练熟。

建议的练法就是你在消息里说的”真实面试官模式”：只问一个具体问题，自己答，然后自己模拟面试官按答案里的”追问解析”往下追 3~8 层。追问不是要背答案，而是逼自己把每条链路的”为什么”讲出来——讲不顺的地方，就是面试会翻车的地方。

如果准备进入这个模式，直接把你想练的第一道题发过来（比如”Java CPU 100% 怎么排查”），我按面试官的口吻只提问、只追问，不提前给考点提示。
